# MAP.md — Codebase Architecture

Single source of truth for the structure of **topiqu-blog**.

Current implementation facts come from source and executable contracts. `PRODUCTION_AUDIT.md`
preserves dated 20–21 October 2026 observations; its historical assumptions and test counts do
not certify this working tree or the live deployment. Current acceptance evidence belongs in
`docs/plans/2026-10-22-optimization-and-production-readiness.md`.

Product work deferred from the current scope is tracked in `ROADMAP.md`.

Bun 1.4.4 is pinned across the package manifest, Docker and CI; Node 24.21.0 is pinned for Nuxt compilation, Vue type checking and browser tooling in `.node-version`, Docker and CI.

Docker uses an app/architecture-scoped Bun package cache and BuildKit APT mounts. The dependency stage stays independent of application source. Host-generated ZenStack output and local test/tool artifacts are excluded from the context; the build regenerates the ORM before Nuxt. Only the prerelease stage copies the pinned Node binary and uses it for Nuxt compilation, matching CI; Bun still installs dependencies, prepares Nuxt, generates ZenStack, packages migrations and runs the released server. The compiler command limits the Node heap to 4096 MiB. Node, its PATH and NODE_OPTIONS are absent from the release stage; Bun keeps its normal runtime defaults. Runtime defaults explicitly set production mode and listen on `0.0.0.0:3000` as `bun`, with its working directory owned by that user. Readiness follows Nitro's `NITRO_PORT`/`PORT` precedence. Image builds never migrate a database; the deployment entrypoint applies committed migrations before starting Nitro and exits if they fail. Production deployment remains operator-controlled.

For the resolved Bun preset only, Nitro's `rollup:before` hook selects `server/runtime/bun.ts`; dev, prerender and other presets keep their upstream entry. This native adapter preserves Nitro 2.13.5's Fetch/websocket handling and owns stoppable Cron handles because the upstream Bun entry has no signal lifecycle. `server/runtime/bunLifecycle.ts` makes `SIGTERM`/`SIGINT` idempotent: stop admission and future ticks, drain HTTP responses, await active scheduled and response `waitUntil` promises, then run every Nitro close hook with all results awaited. `server/plugins/database.ts` disconnects the shared ORM pool; `server/plugins/cache.ts` closes Redis. A shared 8000ms deadline (`NITRO_SHUTDOWN_TIMEOUT`, integer 1–300000ms) bounds drain and close together, and must stay below the platform stop grace. Failed draining skips resource closure under uncertain live requests; deadline/failure exits 1 and timeout force-closes connections. Earlier reported background failures do not change a later clean shutdown's exit status. Persisted task leases remain necessary for abrupt termination and incomplete provider operations; successful draining is not a recovery guarantee.

Nitro's virtual tasks module emits `false` when no schedules remain, so the Bun entry normalizes it with `scheduledTasks || []`. Runtime `TEST=1` also excludes Cron execution through `std-env` while retaining `NODE_ENV=production` for isolated diagnostics. The authored-entry regression exercises both exclusions and positive task dispatch without starting a listener or replacing the global Bun runtime.

`server/runtime/bunBody.ts` bounds actual incoming bytes before Nitro dispatch, independently of HTTP method or claimed length. Shared request limits are 2,000,000 bytes for ordinary bodies and 16 MiB for multipart bodies; the latter includes 1 MiB of envelope space above the largest supported 15 MiB file. Bun's native `maxRequestBodySize` uses the same multipart ceiling. Incremental reads reject excess bytes with 413, release readers/listeners and stop promptly on abort; rejected input never reaches route work. Nuxt Security's secondary header limiter is aligned with the inclusive ceilings, while each upload route still owns its smaller file/format checks. Raw webhook bytes are preserved.

Unused `TurnstileWidget`, `Article/Editor/Chip` and `Article/Editor/Popover`, the unused AI image-tool wrappers and their dependencies were removed. Client/article list-query date validation is shared in `server/utils/listQuery.ts`. MJML 5 rendering for every email template and locale is covered in `tests/server/sendEmail.test.ts`, with SES transport mocked.

The Nitro inline rule for `nuxt/dist` accepts both path separators to work around [Nuxt #36467](https://github.com/nuxt/nuxt/issues/36467): without it Windows builds leave the SSR renderer external and return HTTP 500. Nuxt Image's Nitro 2 integration needs the authored Fetch bridge described below to preserve Bun response headers. The provider's URL parsing, filesystem paths and remote-host restrictions remain upstream-owned. Vite 8 uses Oxc minification to remove production console/debugger statements.

## 1. Stack

Nuxt UI's upstream Popover and DropdownMenuContent use direct Reka component exports rather than the shared namespace barrel, keeping public controls independent of private calendar/date exports. Nuxt DevTools invokes Git through its command runner. These replace the former UI/DevTools Bun compatibility patches; preserve compiled popover, hover-card and locale checks when upgrading these modules.

The Bun patch for Unhead 3.4.3 consumes completed DOM cleanup callbacks. Its upstream renderer retained already-fired callbacks in an older cleanup map; live callbacks shared that lexical context and kept removed meta/link nodes across SPA navigation. Deleting each callback after it succeeds breaks that chain and preserves error ordering. `tests/unit/headCleanup.test.ts` checks real renderer disposal/document switching, title/attributes and event cleanup. Docker copies declared patches before its frozen install. Reassess this patch against the same regressions when upgrading Unhead.

With Nitro 2, Nuxt Image 2.2 selects a legacy IPX Node handler whose raw header writes are lost by Nitro's Bun response shim. The Nitro `build:before` hook recognizes both the module's actual extensionless legacy handler path and its `.js` form, then replaces only that registered handler with `server/runtime/ipx.ts`: public IPX Fetch APIs and H3's `toWebRequest` preserve the returned `Response` headers and conditional requests. Nuxt Image still creates the storage, TTL, aliases and host restrictions; the local bridge adds no parallel image policy. This also avoids the dynamically required `srvx/node` adapter, so no special dependency trace or package patch is needed. `tests/unit/ipxRouteConfiguration.test.ts` loads the installed module to verify its real registration; compiled IPX smoke checks verify the resulting image.

Production OG image resources use `server/runtime/ogFetch.ts` around the installed module's Node fetch binding. The build hook retains that exact upstream transport under a private alias; DNS checks, checked socket lookup, redirect validation and deadlines stay upstream-owned. A byte-counting stream allows at most the shared 15 MiB image limit, rejects oversized declared lengths before reading and cancels/releases a failed stream. The module's existing failure path omits an unavailable image. Redirect/error/null-body semantics are preserved; custom and web bindings are left intact. Tests exercise the installed module registration and actual redirect/body reader with synthetic transport responses, without external calls or dependency patches.

Nuxt UI's component detection generates only themes referenced by app source (including component dependencies). Keep dynamic Nuxt UI component names statically discoverable or explicitly include them in `ui.experimental.componentDetection`. `features.inlineStyles` also inlines global Tailwind/UI/font CSS, removing the blocking entry stylesheet from SSR while preserving styles owned by lazy components. Nitro emits gzip variants of public assets; Brotli stays a CDN concern to avoid expensive build-time compression. The article's related shelf uses native visible hydration with its SSR content intact; header controls and forms hydrate immediately. Release smoke asserts SSR global styles, gzip negotiation and hashed-asset caching.

Responsive media uses explicit `xs` (320px) and `phone` (480px) image breakpoints instead of an unqualified fluid size: Nuxt Image otherwise generates 1px/2px candidates. The Manrope Latin preload has a stable head key shared by SSR and hydration. NuxtLink prefetching starts on pointer/focus interaction instead of importing every visible destination during startup. Consent settings mount lazily on their first opening and stay mounted for closing transitions. Shared browser Zod schemas import `shared/utils/zod.ts`, which disables JIT before schema construction to avoid a CSP-blocked `Function()` probe; server validation retains its default JIT path. Error reporting and CSP remain enabled.

`useDashboardAccess` gates the dashboard layout, header drawer trigger and generation activity together. Ordinary admins need the publication host's resolved site ID to match their active, server-authorized session tenant; platform root/app hosts retain tenant management, while unresolved publication hosts fail closed. Superadmins retain global access. This is UI gating, not a replacement for server membership/scope checks.

- **Public rendering performance:** critical `AppMedia` images are visible in SSR, eager and high-priority, without a JavaScript-dependent placeholder over them. Non-critical images retain lazy loading; actual errors still retry the original source, with a 30-second visible-image stall deadline instead of prematurely blacklisting slow images. Article covers and hero logos explicitly opt into priority; covers include mobile srcset variants. The homepage keeps previously rendered search results during debounce/fetch, applies a query snapshot, replaces first-page results only on completion, and reserves the largest measured result height, capped at one viewport, while filters are active so empty results do not pull lower sections into view. Clearing filters resets that reservation. Dashboard sidebar modules and privileged dialogs are async; dialog modules mount on first opening, initialize their data immediately and stay attached thereafter to preserve close transitions. Tag management captures the opener and explicitly restores keyboard focus on close. Background article-generation UI is restricted to privileged sessions. Nuxt's build manifest disables blanket SSR prefetch hints for unused async modules; rendered-module preloads and NuxtLink navigation prefetching remain intact. These are loading boundaries, not authorization gates.

- **Production boundaries:** generic uploads validate tenant scope and decoded raster content before moderation/storage, normalize media, and use server-generated UUID keys under the tenant/user namespace. Client filenames never select storage objects. Public feed queries share `server/utils/articleCard.ts`'s explicit select; cache namespaces were versioned when internal fields were removed. Authenticated API responses are `no-store`, and the service worker no longer runtime-caches responses; its activation script removes the old `api-cache`.

`server/utils/articleViewerAccess.ts::publicArticleWhere` defines released, published, undeleted article/tenant visibility for public author/tag collections, crawler feeds and external exports. Published translations remain subject to their source article's visibility; Markdown detail uses `canReadArticle` with an anonymous viewer. Administrative previews remain explicit and separate from public counts/exports. Tag-ID reads retain authenticated reader access through the shared public card selection, filtering at the article root before pagination so hidden joins cannot become null records or expose prompts/accounting. Global-tag previews stay within the administrator's active tenant; superadmins retain broader undeleted previews. Author summaries use a versioned payload namespace while retaining their existing generation invalidation.

- **Lifecycle and scheduling:** `requireCron` fails closed for absent secrets. Nitro schedules trial expiry and rotating domain revalidation, and disables scheduling in browser-test builds. Scope/session/public host resolution rejects deactivated tenants; deleting a tenant detaches global identities rather than deleting their other publications. Stripe plan mutations are conditional on the currently attached subscription and reconcile current provider state. Scheduled publication uses a transaction-scoped advisory claim. Translation workers use monotonic timestamp leases, reclaim abandoned work and compare the source article's `editVersion` under a shared row lock before committing; changed sources return to `STALE`, and a replaced worker claim cannot overwrite human edits. The rebuildable media-usage index runs after content commits, so a caught indexing failure cannot abort that transaction.

- **Translation writes and public caches:** manual translation POST is create-only. AI replacement requires explicit replacement intent and the observed translation timestamp; PATCH and DELETE also compare that timestamp and the observed status. Writes affecting live content require `ARTICLE_PUBLISH`. Every writer advances timestamps explicitly because ORM `updateMany` does not do that automatically. Translation changes and tag rename/delete invalidate public feed generations; global-tag mutations collect referring tenant IDs before deleting membership rows and invalidate after the mutation succeeds. Provider usage, audit and announcement failures are reported without classifying already completed translation work as failed.

- **Article text metrics:** `server/utils/metrics.ts::articleTextMetrics` owns the word/200-word reading-time contract for stored HTML and plain text. It preserves inline word joins, separates block/table boundaries, decodes entities and includes saved poll questions/options while excluding scripts, styles, templates, comments and image metadata. Generation savings and the ORM mutation plugin consume the same counts; the plugin preserves explicitly supplied metrics. Financial rate/speed estimates remain in `shared/utils/savings.ts`. Historical values are not rewritten; Markdown is an export format, not the stored body format.
- **Recovery and release:** password reset tokens use purpose-bound HMAC values in Better Auth's existing `Verification` table; consumption, password change, session revocation and DB audit share one transaction. Old reset codes must be reissued. Invitation consumption is guarded inside its membership transaction and never changes a system role. Docker builds are DB-independent and run under `bun`; `scripts/prepare-migrations.ts` packages the existing locked Prisma CLI/native engines, generated ZModel schema and committed migration history inside `.output/migrate`. The unprivileged container entrypoint applies migrations before starting Nitro and exits on failure. A direct DB URL is scoped only to migration execution; runtime keeps its normal URL. Backup/rollout remains operator-controlled as documented in README. The DB pool is bounded, health has a deadline, external logging has a bounded asynchronous transport, and fallback identity rate limits cap memory without evicting active limits.

- **Dashboard UI:** `Header.vue` owns the wordmark, account, interface language, theme and notifications. Its drawer trigger uses the same `lg` breakpoint as Nuxt UI's sidebar; `Sidebar.vue` puts the tenant switcher in its header. Settings and profile use lazy fetches with explicit initial skeleton/error states; late responses initialize pristine forms without replacing dirty edits. `TenantCreate.vue` only allows revisiting steps reached through Continue, and revalidates details before Review.
- **Dashboard setup:** `Admin/SetupChecklist.vue` sits directly above the `Client/Version.vue` bar in one global floating stack, with no header or sidebar trigger. Tenant admins with settings permission can expand/collapse it; the preference is stored per user and tenant. New blogs start expanded, already published blogs start compact, and the entire widget disappears when complete. `buildSetupChecklist` in `shared/utils/siteSetup.ts` checks saved blog branding (name, logo, description), AI author (name, portrait, bio, writing style), focus + audience, an enabled indexed knowledge source, any configured custom domain (including pending DNS changes), and a live published article. AI steps only appear on AI plans. Each accordion row lists concrete requirements and a permission-aware link to the relevant settings, knowledge sources or existing draft. Processing and failed imports have separate states. These recommendations are distinct from the smaller `buildSetupSteps` requirements on the empty publication, where logos and knowledge imports remain optional. `/api/clients/status` uses the request-scoped client, selects only safe author fields, excludes deleted/future publications, and summarizes enabled sources without content. It returns the latest draft slug only to article writers when there is no published article. Article invalidation, knowledge-source changes and saved author uploads refresh the shared status snapshot; the checklist never changes generation or publication settings.

  While an unfinished knowledge step is processing, the widget polls shared status every five seconds, including when collapsed. Polling stops on completion, an error, a tenant/access mismatch or a hidden browser tab, and resumes when the tab becomes visible.

  Publishing setup accepts an active, valid creation schedule or an explicit review of the saved manual/automatic mode; reviewing never enables automation. Measurement, a teammate and an external publishing channel are optional steps. The status endpoint reports only booleans/counts: enabled Analytics with an ID or an active Search Console connection with a property, active human memberships or unexpired/unrevoked invitations, and an enabled Shopify destination blog or an unexpired LinkedIn connection. Tokens, invitation addresses and integration identities are not returned. Skip/restore decisions and manual-mode review are browser-local preferences scoped to the user and tenant, separate from actual server completion; skipped rows have their own status and count as resolved. New integration/member mutations and reopening the checklist refresh the shared status. The measurement action deep-links to the Analytics dialog using `settings?tab=integrations&integration=analytics`. There is no topic-plan editing or AI-visibility measurement step.

- **Domain recovery:** `Admin/DomainVerificationBanner.vue` reads the active session tenant status and displays the existing verification API's TXT/CNAME instructions on the dashboard and branding settings. `/api/domain/pending` also accepts valid, unreserved Topiqu subdomains; activation rechecks availability and domain rules, then uses the same atomic swap and old-host redirect as custom domains. Managed subdomains need no external DNS proof or paid plan. This is an explicit change of canonical domain, not a second simultaneously served address; no schema change is required.
- **Editor navigation:** `pages/admin/editor/[id].vue` owns route middleware/meta, an immediate Suspense boundary and a local error boundary with an explicit reload action. The existing editor lives in `Article/Editor/Workspace.vue`; `Article/Editor/Skeleton.vue` matches its command bar, fields, canvas and desktop panel while the workspace module and article load. SSR still waits for the actual editor. The workspace measures its command bar into `--editor-command-bar-height`; the Tiptap toolbar sticks below it at a lower stacking layer, including when controls wrap. `useClientSiteStatus()` reuses the shared status snapshot on initial consumers and bypasses it for explicit refresh/invalidation.

- **Controversy control:** `Form/Client/ControversyScale.vue` is a discrete 0–3 slider (`NONE`/`LOW`/`MEDIUM`/`HIGH`; empty = 0) on a rounded muted track with inverted fill, checkpoint dots and clickable short labels (`controversyLevel.short.*`). It uses Reka slider primitives because `USlider` hardcodes the thumb `aria-label` and has no value text. Stops are offset like Reka's in-bounds thumb (`12px − p·24px`) so dots and labels line up with it. Covered by `tests/unit/controversyScale.test.ts`.
- **Content settings:** `Form/Client/Content.vue` and `Form/Client/Community.vue` follow the AI tab layout: `h2` page header, then groups with an `h3` outside a card, each group using a different card type (field grid, divided rows, switch rows with icon tiles). Keywords use `UInputTags` with `addKeywords` as the setter for case-insensitive dedupe; language uses `USelect` because `USelectMenu`'s trigger `aria-label` overrides `<label for>`. Covered by `tests/unit/contentBrief.test.ts` and `tests/unit/tenantPublicationSettings.test.ts`.
- **Structured AI output:** use `generateText` / `streamText` with `Output.object({ schema })`; read the validated result from `output`. `server/utils/ai/articleStream.ts` combines the SDK's `stream` activity/errors with `partialOutputStream` drafts so manual generation keeps its progress signals, watchdog and recovery snapshots. The endpoint's NDJSON contract remains unchanged. `tests/server/ai/articleStream.test.ts` covers partial/final output, usage, provider errors, schema failure and reader cleanup with the real SDK and a mock provider.
- **Framework:** Nuxt 4 (Vue 3.5, Composition API), TypeScript strict. Vue component conventions are documented in `CLAUDE.md` under **Code Style**.
- **Styling:** Nuxt UI 4 + Tailwind CSS 4, loaded by `app/assets/styles/main.css`. Reka UI supplies the accessible primitives. Use Nuxt UI components and Tailwind utilities; shared article/table hooks are styled in `main.css`.
- **Article tables** use shared `ARTICLE_TABLE_CLASS` / `EDITOR_TABLE_CLASS` hooks from `shared/utils/articleProse.ts`. `Article/Parsed.vue` wraps published tables in a scrollable surface; `Tiptap/Editor.vue` adds editor-only chrome such as selected cells and resize handles. Both are styled in `main.css`.
- **Article spacing** lives in `main.css`. `ARTICLE_PROSE_CLASS` hides legacy empty paragraphs and trailing line breaks in both the reader and editor preview. `dropBlankLines` normalizes the same markup when saving/generating content.
- **Reading progress is scoped to the article body**, not the full page. `useArticleScrollContext` measures the body rectangle against the active window/dashboard scroller, so comments, sources, related cards and the footer do not pin progress near the beginning and then force a jump to 100% at document bottom. An ancestor marked `data-article-scroller` (the editor preview) takes precedence over the dashboard scroller.
- **`Article/View.vue` is the one article layout** — hero, tags, summary, body, FAQ, series, sources, TOC. `pages/clanky/[slug].vue` adds engagement (follow, likes, share, comments, ads) through slots; `Article/Editor/Preview.vue` feeds it unsaved editor state inside a fullscreen `UModal`. The preview wraps it in `.publication-surface` with `tenantThemeStyle` from `clientsite-status`, because the editor runs on the platform host where `useClientSite()` is `null`. A capture-phase click handler blocks in-app links so the preview never navigates out of the editor. Global `.article-content` rules belong in `main.css`, not a page `<style>`: a page stylesheet only loads with that page.
- **State:** Pinia (`@pinia/nuxt`) + `pinia-plugin-persistedstate`; **Pinia Colada** (`@pinia/colada` + `@pinia/colada-nuxt`) for admin-side data fetching and cache invalidation, see Data-fetching split below. There is no event bus.
- **i18n:** `@nuxtjs/i18n` (`en`, `cs`, `de`, `fr`). Each locale has the same UI namespaces, master administration copy, and email templates. `shared/utils/language.ts` owns supported codes, language tags and picker labels; `shared/utils/routes.ts` owns localized article, tag, author and auth segments outside Vue. The `Language` database enum supports all four codes. Existing tenants with an empty translation target list are migrated to their previous cs/en counterpart; new tenants may select any of the other three languages. The UI language is picked in the account menu (`User/LanguageMenu.vue`, guests too); a signed-in choice is saved to `User.language`, which also selects the language of their emails.
- **Auth:** Better Auth (`server/utils/auth.ts`, ZenStack adapter), argon2 hashing, OTP (`otplib`). See §4 _Auth_.
- **DB / ORM:** ZenStack ORM v3.9 with its PostgreSQL dialect (domain-split `prisma/schema.zmodel` + `prisma/models/*.zmodel` → ignored `generated/zenstack/` TypeScript schema/types, ~50 models). Prisma is not an application dependency; the ZenStack CLI carries Prisma internally only for migration-engine compatibility. See §6.
- **Editor:** Tiptap 3 (custom extensions in `extensions/`: `Poll`, `slashCommand`, `indent`, `figure`, `image`, `aiDisclosure`).
- **Body images are `<figure class="article-image">`** (`extensions/figure.ts`): `Figure` + a single `Figcaption` child, so heading/list commands cannot turn the caption into a block and drop the image. Attributes live on the `<img>` (`alt`, `title`, `width`/`height` = intrinsic size for CLS, `data-media-id`), on a wrapping `<a>` (`href`), and on the figure (`style="width: N%"` = `displayWidth`, `data-align` incl. `float-left`/`float-right`). Parsing accepts only 10–100 % in 5 % steps, the known aligns and http(s)/mailto/relative links (`app/utils/articleFigure.ts`), because DOMPurify keeps any `style`. The legacy AI shape `<p><img><br><small>caption</small></p>` is upgraded to a figure when an article is opened; an image in running text stays the inline `image` node. `AiDisclosure` keeps `<span data-ai-disclosure>` through edits. Selecting an image (the `figureSelect` plugin; ProseMirror only click-selects leaves) shows `Tiptap/ToolbarImageBubble.vue`: alt/title/link (`ImageDetails.vue`, optional write-back to `MediaAsset.defaultAltText`), width presets, alignment, replace from library, delete. `File/TiptapImageFrame.vue` adds drag-resize handles and a missing-alt badge. Floats apply from `sm` up (`main.css`); a linked image navigates instead of opening the lightbox.
- **AI:** AI SDK 7 with `@ai-sdk/anthropic` and `@ai-sdk/openai`. All task, image, embedding and visibility model IDs live in `server/utils/ai/modelRegistry.ts`. OpenAI `gpt-6-luna` through Responses handles article writing, translation, text editing, brief enhancement, LinkedIn posts, backlink outreach and the ChatGPT visibility probe. Other text tasks run on `claude-haiku-5-5`. Article writing and its automatic revision use the saved quality's effort from `shared/utils/articleQuality.ts`: Standard = `high`, High = `xhigh`, Ultra = `max`. Research and editorial/factual reviews use `high`; translations, text edits, short copy, helper tasks and the native Claude visibility adapter use `medium`. `ai/models.ts` picks the provider per task (`aiModel`, `aiWebSearchTool(task, depth)`: Anthropic `web_search_20250305` with `maxUses` 3/5/8, or OpenAI `searchContextSize`). Both providers count reasoning against the output limit, so middleware adds 8k/16k/32k/64k tokens at `medium`/`high`/`xhigh`/`max` to the caller's answer budget; explicitly disabled thinking gets no extra headroom. Haiku rejects `temperature`/`top_p`/`top_k`. Guarded by `tests/unit/aiModels.test.ts`, `tests/server/ai/articleWritingQuality.test.ts` and actual SDK request/response tests in `tests/server/ai/models.test.ts`, without live API calls. Images use `gpt-image-2.5-flare` with explicit `medium` quality; knowledge embeddings remain `text-embedding-3-small` at 1536 dimensions. Visibility HTTP adapters read the central `AI_VISIBILITY_MODELS` registry and run only providers with a configured API key. Optional provider model IDs retain their original values. Reasoning and answer budgets remain explicit at their call sites.
- **Article quality and credits:** `ClientSite.articleQuality` defaults to `STANDARD`; `Form/Client/ArticleQuality.vue` edits the setting through the existing tenant settings form. `shared/utils/articleCredits.ts` prices Standard/High/Ultra at 1/2/3 credits, including review and one automatic revision. Manual and scheduled generation capture quality before reservation and use that snapshot for writing, audit metadata and settlement. The `20261022170000_article_credit_quality_counts` migration lets operations reserve multiple credits while keeping charges bounded by their reservation; deploy it before enabling quality-priced generation. Wallet copy, generation controls and release forecasts use the same price. `articlesRemaining` remains the API field for available credits. `ai/articleUsage.ts` attributes language, image and embedding token usage to an attempt, operation and stage through request-local middleware; USD costing and spend controls are deferred in `ROADMAP.md`.
- **Default editorial author:** `server/utils/ensureAiAuthor.ts` creates or reuses the tenant's oldest active AI author, with a localized publication-based name from `shared/utils/aiAuthor.ts` and the publication logo. Tenant creation calls it inside the existing transaction; scheduled generation and fully AI-authored manual saves also resolve it for older sites. Parent-row locking and collision-safe usernames prevent concurrent duplicate authors without overwriting a customized identity. The existing avatar and settings routes reuse this author.
- Manual generation **streams**: `server/utils/ai/article.ts` splits into `researchTopic` (live-web facts and URLs plus a dedicated YouTube lookup that tries up to three retrieved, oEmbed-verified candidates when selected) / `buildArticleConfig` (Prisma preferences + research-only factual grounding + `articleSchema`) / `finalizeArticle` (licensed Wikimedia/Openverse lookup with progressively shorter archive queries, generated fallback only where editorially safe, then numbered media-slot replacement) / blocking and streaming writers. `POST /api/articles/generate` emits NDJSON progress, the actual reservation, finalized content, then an authoritative `billing` event with the new balance. Events carry outcomes, not just counts: research fallback reason, the YouTube outcome (`found` with oEmbed title / `noCandidates` / `rejected` / `failed` / `researchOff`), per-slot image source (`official` / `screenshot` / `library` / `ai` / `null`), review issues, server-computed `missingModules` on `final`, and `stage` + `creditReturned` on `error`. The client folds them with the pure `reduceGenerationRun` / `generationSteps` (`shared/utils/articleGeneration.ts`) into one `GenerationRun`, rendered by `Article/Editor/GenerationRun.vue` above the title — progress while running, the report (with retry) afterwards; the sidebar only holds the preset form. The run itself lives in the `articleGeneration` Pinia store, not the page: leaving the editor keeps it going, the editor re-attaches by target (`new` / article id) and `Article/GenerationActivity.vue` shows it elsewhere. Leaving a finished, unsaved run on its source language does not ask to discard: the editor writes the author's edits back into the store (`keepGeneratedEdits`), and only saving or dismissing clears it. The store is mirrored to `sessionStorage` and restored after hydration, so a full page load (the public site, a refresh) keeps it too; a run restored as running polls `GET /api/articles/generations/[id]/status` and takes the finished article from the session snapshot, marking the steps it never heard about as `resumed`. A disconnected stream keeps generating on the server; only `POST /api/articles/generations/[id]/stop` aborts it. Internal `[[IMAGE…]]`/poll/video markers are omitted from the streamed editor view; resolved images appear only when ready, while all non-final exits strip every remaining slot. Only slots carry assets: `unwrapContentSlots` lifts a marker out of an `<img>`/`<figure>` the writer wrapped around it, and `dropAuthoredImages` removes images the writer wrote itself.
- The generation report expands the research source count into the existing `Article/SourceList.vue`. Editorial `review-progress` events mark actual live verification, copy-desk review, revision and rechecking; the shared reducer stores the current stage, with a generic fallback for older persisted runs. Transport heartbeats do not count as editorial activity. After 20 seconds without progress, the report shows elapsed seconds since the last actual update, without inventing intermediate progress.
- **Editor sidebar = three tabs** (`Article/Editor/SettingsPanel.vue`, shared by the desktop aside and the mobile slideover through the page's `settingsTab`): _Article_ (cover, sources, series, tags, release), _AI_ (`GenerationForm.vue`, or `AiUpsell.vue` without `hasAiPlan`), _Checks_ (optimization, fact check — locked without an AI plan, since `/api/articles/fact-check` is AI-gated — and media rights; the tab badge shows media needing attention before the score). AI opens first only on a blank article / `?ai=1` / preset prompt; a finished run switches to Checks. Tabs keep hidden panes mounted (`unmountOnHide: false`), but `focusOptimizationTarget` still switches to _Article_ before scrolling, because a hidden pane has no box.
- **No `v-if` on Tiptap bubble menus** (`Tiptap/Editor.vue`). Tiptap detaches their element, so unmounting one breaks Vue's patch and every later update of the page fails silently; generation toggles `edit`, which froze the whole editor sidebar. They hide through `shouldShow` + `editor.isEditable` instead.
- **Library image matching** (`images/selection.ts → matchesImageQuery`) requires the query's identity terms — names and 1–3 digit installment numbers — not every descriptive word; queries without a name need half of their content words. The every-word rule rejected nearly all real photos, so illustrative slots fell through to AI. A named subject is retried as a portrait (`photoSubjectQuery`) for every intent before AI is considered. The cover never stays empty when AI images are allowed: the writer's `coverImage.broaderQuery` (the place, organisation or field) is searched next and credited as illustrative, then a labelled AI illustration follows — for a `photo` subject through `coverIllustrationPrompt`, which excludes people, logos, text and the real event. Body images keep the empty-slot rule. Cron never auto-publishes an article without a cover (`coverApproved`).
- **Vision check of library images** (`images/verify.ts → imageDepicts`): word overlap cannot tell what a picture shows. A Grand Canyon plaque ceremony whose 600-word Commons description mentioned "energy efficient", "retrofit" and "funding" became the cover of a house-insulation subsidy article. Every Commons/Openverse candidate (including the `photoSubjectQuery` retry) is therefore downloaded through the SSRF-safe `fetchPublicUrl` (Openverse `thumbnail` preview, ≤ 4 MB, raster types only) and shown to Haiku (`imageCheck`, thinking off) with the article title and the wanted subject; `photo` intent requires the subject itself, `stock`/`generate` any fitting picture. Stand-ins (cosplay, figurines, statues, merchandise, fan art) are rejected unless they are the article's subject; Commons has little else for fictional characters, so those slots usually stay empty. At most 3 looks per search (`IMAGE_CHECKS`); a rejected candidate moves the provider to its next one, and any download/model failure counts as a rejection. Official press images and store screenshots skip the check: they come from the subject's publisher. Each look is an `image_check` audit step with the verdict. Cost is roughly $0.0001–0.0002 per look. Commons matching also reads only the first 200 characters of `ImageDescription`, since a long description contains half the words of almost any generic query. Provider `accept` callbacks may be async (`ImageAccept`); `createImageSelection().taken` peeks at the reservation without recording it, so a picture is reserved only after it passed the check.
- **Formats propose modules, they do not restrict them.** An explicit module selection passes `selectedModulesFor` / `applyFormat` untouched; `allowedModules` only bounds what the cron topic picker may choose (`topicSchema`). The editor preselects `ARTICLE_GENERATION_DEFAULT_MODULES` on a format change and keeps the author's media choices.
- **The author's first-hand account is testimony** (`AUTHOR_ACCOUNT_RULE` / `AUTHOR_ACCOUNT_VERIFICATION` in `articleQuality.ts`, used by writer, verifier, copy desk and revision). Before it, a first-person story was an unverifiable claim, so the writer produced a "model case" with a disclaimer. Specifics of the case the account does not state (names, amounts, dates, durations, quotes, decisions) must stay general; the verifier flags invented ones as UNSUPPORTED MATERIAL.
- **The article speaks about its topic, not its research** (`editorialPolicy` in `server/utils/ai/editorialPolicy.ts`, shared by writer, verifier, copy desk and revision). A statement that something cannot be verified is allowed only as a correction of a specific claim, a reported unconfirmed status, or a conflict between authoritative sources; otherwise the point is omitted. `aiControversyLevel` sets both the voice and how residual uncertainty reads (NONE/LOW attribute once, MEDIUM/HIGH fold it into the argument). Caveats came from the pipeline, not the writer: research returned an Unknowns section the writer published, and the revision saw advisory NOT VERIFIED verdicts and turned them into qualifiers. Research now lists only corrections, `revisionEvidence` drops NOT VERIFIED lines before revision (they stay in the audit), and the copy desk reports remaining caveats as blocking `hedging`. A `story` is narrated in scenes and framed once as illustrative; research gathers the real process it passes through instead of checking the plot, and the copy desk may not demand its documentation. Stories read as fact sheets with a protagonist walking through them (a body disclaimer about what is fictional, "a study notes" attributions, word definitions, an invented phone screen to carry a requested table, an options list), so `STORY_CRAFT` in `formats.ts` sets the writer's scene rules: the illustrative frame lives in the perex only, fictional characters may speak invented dialogue (real people never do), research enters as what the protagonist meets, modules sit between scenes as plain sidebars, and HIGH controversy puts the voice in a sardonic narrator. The copy desk reports those failures as `broken_structure`; a list in a story body is a deterministic issue. A requested video is owed only when research appended a `Verified YouTube video` line (deterministic check); otherwise the desk may not report it missing, since the writer cannot invent a URL. Story video research searches the real subject (character, franchise, place), not the invented plot. After a verified revision the follow-up desk pass (`factsChecked`) treats its own `unsupported_claim` as advisory and blocks only `invented_detail` (a quote, number, date or source absent from the grounding); the editor shows those remaining issues instead of a green review step. Measure with `bun run eval:ai` (`tests/eval/`, live model calls, skipped in CI).
- **Assignment fidelity is part of editorial approval.** `editorialPolicy` carries `aiToneOfVoice` to writer, copy desk and revision; an explicit tone in the article assignment overrides the publisher default. An opinion develops the requested stance, including requested profanity, without interpreting profanity alone as violent intent or replacing the article with a civility/nonviolence lesson. HIGH opinion/story explicitly retain the confrontational voice the topic and tone call for, without mandatory balancing paragraphs or conciliatory endings; substantial unsolicited softening is `assignment_mismatch`. A civil assignment still overrides a profane publisher tone. Shared `AUTHORIAL_REASONING` distinguishes expressive hyperbole from concrete factual allegations for the verifier too; factual repairs preserve the rest of the argument's force. `articleQuality.ts` treats substantive `assignment_mismatch` as blocking even after factual verification, using the existing single revision and follow-up review. Factual corrections remain required; minor style differences are advisory. The manual editor retains an unapproved draft and shows the issue, while scheduled auto-publication still requires editorial approval. `tests/eval/articleVoice.test.ts` uses the production model/search adapters, runs tenant fixtures sequentially, checks known bad and good review examples, and saves both article versions plus a separate voice rubric assessment for human inspection. Rubric judgments are model assessments, not proof of correctness.
- **AI edits** (`shared/utils/aiEdit.ts`, `server/utils/ai/enhance.ts`): `POST /api/articles/generate/enhance` takes an `action` for the brief (`questions` returns questions whose answers are appended as the author's details; `sharpen` / `shorten` / `grammar` rewrite it). `POST /api/articles/rewrite` edits a selected prose passage from the Tiptap text bubble (`useTiptapRewrite`); input and output go through `sanitizePassage` (prose tags + `href` only), and a range the author changed meanwhile is not overwritten. `improve` requires a free-text `instruction` (`TiptapRewritePrompt`). The toolbar's whole-article variant sends only the text runs of paragraphs and headings as `blocks` (`documentTextPassages`) and writes them back in place, so images, tables and embeds are never round-tripped through the model; a different block count is rejected. The writer keeps verification internal: a stale premise is corrected once rather than turning the article into repeated caveats. Provider usage is logged per run to `AiUsage`, including aborted runs. Selected format/modules/depth are audit-stamped from the start through completion or abort.
- In the manual editor, generation passes the selected language to the server and the writer uses it explicitly; changing language tabs is disabled during a run. `Article.language` records each article's source language independently of `ClientSite.language`; the selected new-article tab supplies it, recovery drafts remember it, and existing articles keep it fixed. Public cards, detail canonicals, sitemap, RSS, external APIs, and translation targets use the article language, so an English-first site can publish a Czech-only article at its Czech URL. Existing rows receive their site's language in migration `20260927180000_article_source_language`; a database trigger supplies it for older app replicas during rollout. The sticky editor bar keeps the current stage and elapsed time visible while the settings pane scrolls. Optimization results are hidden during streaming and recalculated from the final editor content. `useArticleDrafts` keeps the returned `ArticleDraft.id` and sends it on later autosaves so one editing session updates its recovery draft; `POST /api/articles/draft` scopes that update to the signed-in user and tenant. Article creation checks AI-suggested tag IDs against the tenant before connecting them, dropping unknown suggestions rather than failing the article write. A cover credit JSON object contains `kind`, which ZenStack's CREATE policy parser mistakes for a query node; the create route writes the credit with an UPDATE inside the same article transaction.
- **Scheduled editorial variety stays inside the existing topic-selection call.** `server/utils/ai/formats.ts` holds six broad formats, several dramaturgical variants per format, and each format's eligible modules (`answer`, takeaways, FAQ, poll, table, body images, YouTube). `topicSchema` requires one to four useful modules but mandates no particular type; cron respects that exact filtered selection, so images, videos and polls remain topic-dependent rather than universal filler. The writer receives the variant's progression and `applyFormat` clears unselected structured modules. `server/utils/ai/articleQuality.ts` is the independent copy desk for scheduled output: it checks factual grounding, repetition, filler, artificial time framing, specificity and natural wording, requests one full revision when needed, then reviews again. A failed or unavailable final review forces the article to draft even when auto-release is enabled; `news` and every topic marked time-sensitive additionally require a completed live-research pass with at least one retrieved source. The cron feeds the picker the last 12 realised signatures (including table/image/video detection from body HTML), persists format/variant, and emits one compact generation audit with requested/delivered/missing modules plus media counts and the editorial verdict; token billing includes research, review and revision calls. Its monitored result reports per-site outcomes, failures with stages, and aggregated skip reasons instead of dumping unrelated skipped tenants. Search Console opportunities remain best-effort prompt enrichment.
- **Release schedule = one slot planner for every rhythm.** `ClientSite.generationFrequency` is `DAILY` / `WEEKLY` (local `releaseHour` ±`FIXED_JITTER_MINUTES`) or `INTERVAL` (a random gap of `intervalMinHours`–`intervalMaxHours`, min 6 h, landing inside the local `releaseWindowStart`–`End` on `releaseDays`), all in the tenant's `timeZone`. Slots come from the pure `shared/utils/releaseSchedule.ts → nextRelease` (`tests/unit/releaseSchedule.test.ts`), which the settings preview (`Form/Client/ReleaseSchedule.vue`, seeded so examples stay put) and the credit forecast reuse. The chosen slot is stored in `nextReleaseAt`.
  - `generate-article` runs every 15 minutes and picks sites whose slot is within `GENERATION_LEAD_MS` (3 h). `planRun` (`server/utils/generationSchedule.ts`) decides; a guarded `updateMany` on the read `nextReleaseAt` claims the slot by writing the following one before any AI call, so overlapping runs cannot double-generate. A failed run forfeits its slot instead of retrying on our AI bill; a site out of credits keeps it and generates after the top-up.
  - An approved auto-release article is saved as a draft with `releaseAt = slot` plus its media-rights snapshot, and `publish-check` releases it — the same path as a human-scheduled article. A slot already in the past publishes at once. Without auto-release no `releaseAt` is set, because `publish-check` publishes every draft that has one.
  - Stock origin follows the licence (`stockOrigin` in `articleMedia.ts`): CC0, `Public Domain Mark` and Commons `PD-…` register as `PUBLIC_DOMAIN`, other `CC …` (except NC — a tenant blog is commercial) as `CREATIVE_COMMONS`, anything else as `EXTERNAL`, which always needs a person to confirm. Store media registers as `PUBLISHER` (uploaded by the publisher for promotion; cleared with a source): `images/stores.ts → STORE_MEDIA` lists each store's CDN host and path, and an image counts by its own URL or, once re-hosted from an official page, by its credit's `sourceUrl`. Steam and the App Store (iTunes Search API) are searched directly; GOG, Epic and Google Play have no documented public API, so their media arrives only through a store page the research returns as `OFFICIAL MEDIA`. Press-page images and YouTube thumbnails stay `EXTERNAL` unless a licence is declared: a schema.org `ImageObject.license` per image, or the page's `rel="license"` for files on the page's own host (`press.ts`, `ccLicenseName`). A re-find upgrades an unconfirmed `EXTERNAL` asset to the more specific origin (`registerMediaAsset`). With auto-release on, generation passes `requireClearRights`: providers (`ImageProvider.search` `accept`) skip candidates whose prospective asset fails `mediaRightsIssues` and try the next real one; AI comes only after every real candidate, and if it is unavailable the cover falls back to an unclear real image so the article waits for review. Photo slots never get AI, they are dropped.
  - A site without a slot (migrated DAILY/WEEKLY, or scheduling re-enabled) gets one measured from `lastGeneratedAt`, so the deploy never fires an extra article. A settings change to any `RELEASE_SCHEDULE_FIELDS` is validated as a whole (`releaseScheduleError`) and restarts the rhythm from now; revoking `ARTICLE_CRONS` clears the slot.
  - `CRON_ARTICLE_SKIPPED` carries an idempotency key per slot (or per day without one), so the 15-minute cadence logs one entry per missed slot.
  - An `insufficient_articles` skip emails the tenant's verified owners and `BILLING_CHANGE` members (`server/utils/creditsDepleted.ts`, template `emails/templates/creditsDepleted.mjml`). The `CREDITS_DEPLETED_NOTIFIED` audit key names the newest credit grant, so it sends once per depletion and a top-up re-arms it; the audit row is written after sending, so an SES failure retries next run.
- **Automatic article series are opt-in and retrospective, not speculative.** `ClientSite.aiSeriesEnabled` enables a conservative classifier after a scheduled article is finished; `server/utils/ai/articleSeries.ts` may attach it to an eligible recent series or create one only by grouping it with one or two real, recent standalone `FULL`-AI articles. The server revalidates IDs and cadence inside the article transaction. One series must sit out the next two articles and may occupy at most three of the last ten; at most three AI-created series may be active, and only one new AI series may be created per ten-article window. A series absent from that window becomes dormant automatically, so there is no planner or open/closed lifecycle to maintain. Classification failure degrades to a standalone article. Manual series edits are unrestricted, and the existing selector owns rename/delete recovery.
- **Internal links are a separate pass after writing, never the writer's job.** The writer is told not to link the publication. `server/utils/ai/articleLinks.ts` (`linkArticle`, cron and manual stream) shows a cheap model the finished paragraphs plus up to 40 published same-language articles (all of them on most sites; above that, shared tags then recency decide, so no embeddings). The model returns `{paragraph, anchor, articleId}`; `insertArticleLinks` keeps a link only for an offered ID whose anchor is verbatim whole-word text in a body `p`/`li` (not captions, quotes, tables), max 3, one per paragraph and target. Zero links is a valid result; failure returns the body unchanged.
- **Article links are stored as written and resolved at render.** `server/utils/articleLinks.ts` (`resolveArticleLinks`, article GET blocks and `/md`) parses `/{lang}/{segment}/{slug}` (`parseArticlePath`), follows `ArticleSlugRedirect`, points to the published translation in the reader's language (else the original) and unwraps links to unpublished or deleted articles. It covers hand-written links too, so there is no `data-article-id` to keep alive through TipTap or translation. The editor's `content` stays unresolved. The `internal-link` optimisation check counts only links to an article, not the homepage.
- **Search Console Autopilot is an explicit write opt-in, gated by active `SEARCH_CONSOLE` + `AI` features (PREMIUM; configurable CUSTOM).** The nightly `search-console-sync` stores finalised `date/page/query` performance, then `search-console-autopilot` atomically claims each opted-in connection and changes at most one published article per day. A page-one query with ≥200 impressions and CTR below 2% may rewrite only title+excerpt; a position-4–20 query may append one focused section. Audit history enforces seven days between writes to one article and 30 days for the same article/query pair. Existing article URLs are removed from the new-article signals sent to `generate-article`, preventing the obvious cannibalisation path; growing uncovered queries may reprioritise that cron but cannot override focus/novelty. Every write stores before/after data in the immutable audit chain, invalidates feeds, stales translations and exposes a guarded rollback that refuses to overwrite later human edits. Losing either feature disables the opt-in, so it never silently resumes after a downgrade.
- **Image model note.** `articleImage` moved off **Imagen 4 Fast** because Google shuts the Imagen family down on **2026-08-17**; `tests/unit/aiModels.test.ts` now fails on any `imagen-*` id so it cannot come back. Nano Banana 2 Lite is a **Gemini image model** (`:generateContent`), not an Imagen one (`:predict`) — `google.image()` fronts both, so `models.ts` is unchanged, but Gemini image models ignore `n`/`maxImagesPerCall` (dropped from `ai/image.ts`) and return PNG rather than WebP, which `imageExtension(output.image.mediaType)` already handles.
- **Cloud / Infra:** AWS S3, Rekognition and SES; the server Stripe SDK through `server/utils/stripe.ts`; self-hosted Dokploy/VPS packaging through `Dockerfile` (multi-stage Bun, `NITRO_PRESET=bun`); PWA (`@vite-pwa/nuxt`). The unused Nuxt Stripe module was removed; billing still uses the server-owned singleton. OG images use Takumi and PDF routes use PDFKit, without a browser renderer. Playwright is development/CI tooling for browser verification. Deployment and migration ordering are documented in README and `docs/operations/production-workflows.md`; the deleted serverless migration playbook is historical.
- **Media Library:** `MediaAsset` is the tenant-owned reusable asset record for uploaded, externally referenced, stock and Topiqu-generated media; storage remains in S3/CDN, while external and stock assets are hotlinked. `/admin/media` and `components/Media/{Library,Picker,Detail}.vue` share search/filter/select behavior across cover and body images. `ArticleMediaUsage` is a rebuildable index of HTML/cover references, not the source of truth; indexing failures cannot undo a persisted article. Routes enforce active tenant capabilities and constrained lookups, and selected cover IDs are revalidated server-side. Rights/provenance remains on `MediaAsset` for both the library and pre-publish checks.
  - Library reads reuse SSR payloads and isolate concurrent pickers with an instance/user/tenant key. Filter changes refresh that record through a scoped watcher; reactive query refs stay out of Nuxt's retained options. `app/utils/asyncDataRequest.ts` owns a disposable callback outside component setup so inactive Nuxt async-data closures cannot retain the picker and its parent editor after unmount. Public author/tag/related feeds share that boundary through `useArticleFeed`. Default factories in `app/utils/asyncDataDefaults.ts` retain only plain initial data and return fresh lists/nested data. History, tag/follow queries and currency reads keep retained options separate from component-owned getters/models. Nuxt 4.6 still leaves small inactive records; this does not purge its private registry. The resource protocol uses native time and explicitly disposes chooser handles; its File/DataTransfer assignment avoids Playwright 1.64.1's additional internal retargeted handle. Before/after memory evidence must distinguish application ownership from those instrumentation roots.
  - Deletion is archive-first and refuses known references. The scheduled `media-gc` reviews at most 100 due requests, checks references across tenants/shared objects and guards updates against changed archive requests. Referenced objects are retained; unreferenced objects stay quarantined, with physical `purged: 0`. Bytes are retained because HTML writers currently commit before best-effort usage indexing, so a remote delete cannot exclude a new reference safely.
  - `scripts/backfill-media-library.ts` is dry-run by default and registers legacy media/enriches records/rebuilds usage rows. Its `assets → articles → translations → drafts` phases share a bounded row budget; batches are capped at 200, document bodies at 1 MiB/500 occurrences, candidate matches at 1000 and new asset identities at 20,000 per invocation. Resume the same tenant/filter with emitted `nextCursor` (`PHASE:LAST_ID`, or a bare phase); `null` means completion. Oversized, ambiguous, deleted and concurrently changed rows remain intact. Each document's apply-mode asset registration and usage replacement is atomic, preserving existing rights/archive/provenance metadata. Dry-run proposal deduplication is per invocation. Apply mode requires review and separate authorization against an identified target; it is not a build or startup operation. README documents the operator commands.

Standalone CLI/runtime dependencies and Vue macro type imports remain explicit.

- Confirmations use one `AppConfirmDialog.vue`: `useConfirm()` returns a boolean through Nuxt UI's overlay provider; declarative dialogs use `v-model:open` and `@confirm`. The filesystem and route registry are authoritative rather than a manually maintained page count.

    - While there: `api/tags/slug/[slug].ts` selected each article's author with `user: { omit: { password: true } }`, which only drops the `@omit`-ed secrets and shipped the rest of every author row (`email`, `emailVerified`, `lastLogin`, `role`, `clientSiteId`) into the SSR payload of a **public** tag page. `ArticleCardData` only ever reads `user.username`, so it is now an explicit `select: { username: true }`, matching `by-author`. Rule of thumb this encodes: `omit` is a deny-list and leaks by default — public projections must be `select`.
  - `index.vue` — tenant homepage. The featured response is awaited for the SSR lead story and published-article count; the archive remains lazy. A zero-article site renders the dedicated empty page, while a failed featured request renders a retry alert. Sections with no articles, tags, popular stories or poll are omitted. Unfiltered archive cards exclude the lead selection, while filtering searches the full feed. The filtered empty state uses `articles.home.noMatches`.
    - The shared editorial layout keeps the large publication hero: logo, name, tagline and description beside the lead article and a small topic/count rail. Its scroll cue moves to the next content section. Recommendations, the series shelf, topic filter, article archive, discussions and popular/poll area follow. The featured endpoint returns three public, tenant-scoped articles ordered by views after excluding the lead selection, so the lower popular list does not rank only the first feed page. The lazy feed keeps search and pagination, and resetting its visible rows on locale/filter changes prevents stale-language cards.
    - The default layout publishes the tenant's color and typography through the publication theme tokens; Nuxt UI controls and homepage links use the same `primary` accent rather than a fixed platform color.

The count is SSR-available and payload-transferred, so the first HTML and hydrated view agree; the feed request is skipped for that tenant. The count uses the server's published-article scope rather than the resolved feed, and a network error never masquerades as an empty site.
    - **Empty state is audience-split** under `Article/Empty/` — `Page.vue` is the shell (centred full-height section, gradient/dot backdrop, logo or name monogram) and picks one of two bodies by `isOwner`. `Visitor.vue`: site name as `h1`, description, a "coming soon" pill (`articles.empty.badge`) and `articles.empty.title/message`. `Owner.vue`: an "only you can see this" badge, `articles.empty.owner.*` copy stating that visitors see this page and that it is `noindex` until the first article, primary/secondary CTAs to `admin-editor-id`/`new` (the second with `?ai=1`, which the editor reads to autofocus its AI composer — the panel itself is always visible now), plus a **launch checklist** with a progress bar. `isOwner` is `role === 'superadmin' || (role === 'admin' && user.clientSiteId === clientSite.id)`, so an admin of _another_ tenant sees the visitor copy.

Both the empty-publication checklist and the dashboard layout use the same completion rules: a nonblank description, focus + audience on AI plans only, an unverified custom domain when applicable, and a live published article. Logos and knowledge imports are recommendations rather than progress requirements. BASIC has two steps on a managed subdomain; an AI-capable plan has three. Unfiltered cards exclude the lead and recommendations, so a one-article site does not show a redundant empty archive; an active filter searches the full feed. Loading, failed, filtered-empty and pagination states remain distinct.
    - **Thin-content `noindex`.** `server/api/articles/featured/[slug].ts` returns the `totalArticles` count it already computed, and the page emits `robots: 'noindex, follow'` until that count is non-zero, so an unpopulated tenant homepage is never indexed as thin content. The count comes from enhanced Prisma, so for an anonymous crawler it is the _policy-visible_ (published) count — exactly the right signal. - **Data-fetching split (HARD RULE)** — two layers, chosen by whether the response is SSR/SEO-critical:
  - **`useFetch` / `useAsyncData`** for public, SSR-rendered, SEO-critical reads (`pages/index.vue`, `clanky/[slug]`, `stitky/[slug]`, `autor/[name]`, `useClientSite.ts`). These depend on the Nuxt payload, `getCachedData`, and blocking-vs-lazy semantics that drive `robots` meta — do not migrate them.
  - **A `useFetch` payload you write back into needs `deep: true`.** Nuxt 4 defaults `deep` to `false`, so `data` is a `shallowRef`. `pages/clanky/[slug].vue` writes `likes`/`shared`/`followerCount` back into the article after each action; a `triggerRef` re-renders the page but `Article/ActionsBar.vue` gets the same object identity, so `hasPropsChanged` bails and the counts only moved on a manual refresh. A `triggerRef` beside a `useFetch` payload is therefore a symptom, not a fix.
  - **Pinia Colada (`useQuery`/`useMutation`)** for client-only admin CRUD behind auth. Rationale: those endpoints are per-user and per-tenant (policy-scoped through `getEnhancedPrisma`), so they can never be cached server-side (ISR / `defineCachedEventHandler` / `server/utils/cache.ts`, whose invariant forbids personalised data) — a shared cache there would be a cross-tenant leak. Colada's cache lives in one authenticated user's tab, so isolation is structural.
  - **Query keys are centralised** in `app/utils/queryKeys.ts` and are the invalidation contract; the prefix hierarchy (`['articles'] ⊃ ['articles','list'] / ['articles','detail',id] ⊃ …tags / …available-tags`, plus `['clients']` and `['stats']`) is pinned by `tests/unit/queryKeys.test.ts`, which also asserts the three roots can never invalidate each other. Never inline a key literal at a call site — a wrong key surfaces as _stale UI_, which is a worse failure than the over-fetching it replaces.
  - **SSR + auth:** queries must fetch via `useRequestFetch()`, not bare `$fetch` — Colada prefetches on the server via `onServerPrefetch` and bare `$fetch` does not forward the session cookie (401). Mutations are client-only and use plain `$fetch`.
  - **Global defaults live in `colada.options.ts`** at the repo root, **not** in `nuxt.config.ts` — the module declares `configKey: 'colada'` but reads a root-level file, and silently falls back to `export default {}` if it is missing. `staleTime` is 300 s (library default is 5 s, which would refetch on practically every remount and defeat the point of the cache); `gcTime` 30 min. The module also auto-imports `useQuery` / `useMutation` / `useQueryCache`, so do not import them explicitly.
  - **Every query renders three states.** A failed fetch must never fall through to the empty state — before this was fixed, a 401/500 left `data` undefined, `rows` empty, and the table showed _"no articles"_ for what was actually a broken request. Each migrated component derives `loadFailed` from `error` **and** an absence of data (so a refetch failure over `placeholderData` keeps the stale rows visible instead of blanking them), and offers `refetch()`.
  - **Route-type blowups:** typing a query as `requestFetch('/api/…')` can trigger `TS2321 Excessive stack depth` — Nitro's route-matching types leak into Colada's generic inference. Fix by passing an explicit generic sourced from `InternalApi['/api/route']['default' | 'get']` (`nitropack/types`), which keeps the real response type without re-resolving the route. For mutations, an `async … => { await $fetch(…) }` body (concrete `Promise<void>`) is enough.
  - **Cross-component invalidation** goes through `useCacheInvalidation()` (`app/composables/`), the single place that maps a domain event to the keys it dirties (e.g. creating or deleting an article dirties `articles` _and_ `stats`; editing dirties only `articles`; a tag edit dirties just that article's detail). Call it directly after the mutation — do **not** reintroduce an event bus.
  - **`mitt` is fully removed** (`useArticleEvent` / `useClientEvent` deleted, dependency dropped). It was only ever a cache-invalidation mechanism — every handler was a bare `refresh()` — and it had two structural faults Colada does not: the module-level emitter leaked one never-removed listener per SSR render and per remount, and an event was lost entirely if the interested component happened to be unmounted. Colada marks the cache entry stale instead, so a closed dialog refetches correctly the next time it opens.
  - **Two components read the same article tags**, so they must share a key: `Article/Tag.vue` (the modal off the article table) and `Tags/Manager.vue` (embedded in `Article/Modal.vue` and the editor) both hit `/api/articles/:id/tags` and are both keyed `queryKeys.articles.tags(id)`. They previously held two independent caches, so adding a tag in one left the other stale — and `Article/Modal.vue`'s `invalidateArticleDetail()` only reached half its own subtree. `Tags/Manager.vue` keeps its local `tagBuffer` staging model (it doubles as the create-mode tag picker, where no article exists yet and the parent persists on save); the query only seeds it, gated by `enabled: () => !!props.article?.id`.
  - **Creating a tag dirties two roots** — the article's detail _and_ `['tags']`, the tenant tag catalogue behind `/api/tags` shared by `Tags/Manager.vue` and `Tags/Create.vue`. `Article/Tag.vue`'s create mutation invalidates both.
  - `Tags/Create.vue` (sidebar "Manage tags") is one field that filters and adds (adding is refused on an exact name match) over a chip cloud; clicking a chip name swaps it for an input — Enter saves, blur keeps a valid rename and drops an invalid one, and Escape is caught in `UModal`'s `onEscapeKeyDown` so it cancels the rename instead of closing the modal. Its `useFetch` is `deep: true` because the optimistic edits mutate the list in place.
  - **Migrated:** `Article/Table.vue` and `Client/Table.vue` (keyed pagination, `placeholderData`, debounced search feeding the key, refetch dimming + `aria-busy`; the article table also has row skeletons), `Article/Tag.vue`, `Tags/Manager.vue`, `Stats/Dialog.vue` (dashboard + sentiment, the latter gated by `enabled: () => !isBasicPlan`). Mutation sites (`Article/Modal.vue`, `Client/Create.vue`, `pages/admin/editor/[id].vue`) invalidate rather than emit. Still on `useFetch`: `User/List.vue`, `Tags/Create.vue`, `Client/Users.vue`, `Client/Version.vue`, `User/Activity.vue`, `Notification/Bar.vue` (the last is a hand-rolled infinite scroll — `useInfiniteQuery` + `refetchInterval` candidate).
- **Connection state is a state, not a toast** — `Network/Indicator.vue` (mounted once in `app.vue`) keeps its pill up for as long as the connection is down and only auto-dismisses the recovery, which reuses the same mounted pill so red→green is a color transition rather than two separate notifications. The visibility machine is `composables/useNetworkPill.ts` (`tests/unit/networkIndicator.test.ts`); the component only maps state to an icon and a surface. A single shared timeout meant a drop landing mid-recovery inherited the pending dismiss and hid itself after 3 s while still offline.
- `stores/` — Pinia (`theme.ts`); persistence handled per-store via plugin.
- `layouts/`, `middleware/`, `error.vue`, `app.vue` — standard Nuxt scaffolding. The global `Header.vue` is a fixed `h-18` overlay: content-heavy public pages own their hero spacing, while app pages (`admin`, `master`, `settings`) reserve the header plus their intended gap explicitly; Settings navigation sticks at `top-24`, and the editor header at `top-18`. Making the global header participate in flex layout duplicates the homepage's existing clearance and makes descendant sticky offsets slide behind it. One other load-bearing detail in `layouts/default.vue`: the root wrapper is `overflow-x-clip`, **not** `overflow-hidden`. `hidden` makes that box a scroll container, and `position: sticky` resolves against its nearest scrollport — a box that is exactly as tall as its content and therefore never scrolls, so every sticky descendant silently degrades to static while the page scrolls past it. That killed the article editor's sticky header (taking Save/Publish off screen the moment you scrolled into the body), the Tiptap toolbar, the homepage filter bar and `Footer.vue` — all four had been written as sticky and none of them stuck. `clip` still contains horizontal bleed, which is the reason the class is there next to `max-w-screen`, without establishing a scrollport (and `overflow-y` stays `visible` beside `clip`, unlike beside `hidden`). Don't swap it back.
- `assets/styles/` — global `main.css`, loaded through `nuxt.config.css`, imports Tailwind CSS, Nuxt UI and variable fonts. It owns shared theme tokens, publication and article styles, and editor/vendor overrides.

### Auth (Better Auth)

- Development auth accepts HTTP loopback origins, including `*.localhost` tenant subdomains on development ports. Production keeps the existing Topiqu origin allowlist; local session cookies remain host-only.
- `server/utils/auth.ts` is the instance; `getSessionUser(event)` (cached on `event.context.authUser`) and `requireUser` are the only server entry points. Client state is `useAuth()` (`app/composables/useAuth.ts`), filled by `app/plugins/auth.ts` during SSR; the Better Auth client library is not shipped.
- `server/api/auth/[...all].ts` forwards only an allowlist of paths. Better Auth also mounts `/update-user`, `/change-email`, `/link-social`, … which would bypass our validation, and `disabledPaths` only matches exact paths.
- Credentials and the onboarding token are a local plugin (`/sign-in/credentials`, `/sign-in/token`): passwords stay on `User.password`, so there is no credential `Account` row. `Account` holds OAuth identities only.
- Sessions are DB rows (`Session.token`, `@omit`-ed; the adapter gets a client with that omit lifted). Revoking deletes the row, so there is no revocation middleware. `databaseHooks.session.create` blocks deactivated users and stamps device, geo and the initial tenant (`initialTenant`); `customSession` → `toSessionUser` derives role/plan/tenant/scopes per read and drops a tenant the user left.
- **Session role `admin` means "any active member", not a permission.** ZenStack policies only see that role, so a member with zero scopes passes them. Every tenant-admin route must call `requireTenantScope` (or `requireArticleAccess` / `requireDomainAccess` / `requireShopifyAccess` / `requireWebhookAccess` / `resolveAiUser`); `hasTenantScope` gates fields and secondary checks. `SessionUser.scopes` (owner/superadmin: all) feeds `useTenantScope()` for UI gating only. `tests/server/tenantGuardWiring.test.ts` fails on a non-GET route with no guard unless it is in its exemption list; `tenantScopeMatrix.test.ts` runs handlers without each scope and expects 403 before any write.
- OAuth: a new user needs a verified provider email (`user.create.before`); linking to an existing user needs both emails verified (neither provider is trusted). Failures redirect to `/auth-error`, which maps Better Auth codes in `shared/utils/authError.ts`.
- Audit: `logAction` writes `Log` rows under an HMAC hash chain (advisory lock) and mirrors them to the logger as `audit:<action>`. The account Security panel shows only session/password/role events, and `/api/clients/:id/log` keeps a compact whitelist, so generation steps and config diffs stay out of both. `ARTICLE_GENERATION_STEP_*` / `ARTICLE_GENERATION_FALLBACK` (`articleGenerationAudit.ts`, keyed by `attemptId`/`mode`/`stage`) are best effort and never carry prompts, briefs, article bodies or provider responses. `CLIENT_SITE_UPDATE` logs only changed fields as before/after through a whitelist (`auditChanges`), so API keys and DNS tokens never enter.
- Better Auth's rate limiter is off: it keys on the first `X-Forwarded-For` entry, which is the Cloudflare edge here. `checkLoginRateLimit` (`clientIp`) and the `nuxt-security` limiter on `/api/auth/sign-in/**` cover it.

### Keyword plan and news (`server/utils/keywords/`)

- Enrichment for the `generate-article` topic picker, never a prerequisite: failures log and fall back to "none". Everything needs DataForSEO credentials; outside production `dataforseo.ts` calls the free sandbox.
- Principle: keyword names, demand and news come from DataForSEO data; models judge relevance/reader intent or pick from that data. `keywordSeeds` rewords the tenant's own focus into niche search phrases; `keywordOpportunity` proposes an angle only for supplied queries. Provider spend is logged per rebuild; caps are five Labs requests and thirty SERPs plus the seed/scope/opportunity model calls.
- Rebuild steps: Labs `keyword_suggestions` per seed (max 5, `allSettled`, fails only if all fail); `dataforseo.ts` preserves all task results because the seed and suggestions can be separate. The focus supplies additional niche seeds even when the tenant already has keywords. Clusters merge word-order/accent variants; demand is the head keyword's volume, never a sum of potentially overlapping synonym searches. Navigational intent is dropped and transactional intent discounted. Up to 250 candidates pass `inScope` before the top 30 are selected, so popular off-topic terms cannot crowd out a narrow niche. Every selected candidate gets a best-effort SERP (PAA, AI overview, domains and up to five organic titles, snippets and URLs).
- Scoring (`clusterScore`): demand × ease × intent × reach × timing. Commercial intent counts fully and ×1.2 when the tenant has a product catalog (`KnowledgeProduct`); transactional ×0.6, since "buy X" wants a product page. Timing comes from Labs `monthly_searches`/`search_volume_trend`: a seasonal peak (≥1.5× the yearly average, `peakMonth`) 1–3 months ahead ×1.25, out of season ×0.8; yearly trend ±50 % nudges ×1.15/×0.85. Candidates sharing ≥3 top-10 URLs merge into the higher-priority one (`groupBySerp`), and a query where the blog already ranks top 10 is not planned as a new article (pins excepted).
- `opportunity.ts` runs one `keywordOpportunity` assessment per plan: exact audience fit, editorial search intent, the unanswered reader need, coverage against up to 200 published/draft titles and excerpts, and duplicates within the proposed plan. Login/official-site/checkout/listing searches and already-covered needs are rejected. Accepted topics persist a concrete angle, a localized one-sentence reason and the evidence in `KeywordCluster.opportunity`; missing organic evidence is always marked possible, not a strong opportunity. The same need/reason reaches the topic picker and writer. An incomplete or failed assessment leaves the existing plan intact. No model predicts visitors or ranking guarantees.
- Assessment uses the dominant SERP meaning (a franchise keyword does not license TV coverage for a games blog; a song-named coffee query does not prove coffee demand). Specific questions/comparisons receive priority over broad brands/categories; broad queries receive a score multiplier of 0.35. Reasons cannot invent competitor omissions from titles/snippets. Seed generation, scope classification and opportunity assessment use medium reasoning with separate answer budgets and middleware headroom. Usage is recorded before reading structured output so incomplete responses remain observable.
- Refreshes are monthly, on profile/language/market changes, or when fewer than three assessed topics remain — daily only if the last rebuild found at least three (counting those used since), otherwise after 7 days, so a narrow niche does not pay for the same few topics every day. `ClientSite.keywordPlanAttemptedAt` claims paid work with a one-day retry cooldown; `keywordPlanRefreshedAt` records only successful refreshes. A versioned profile binds usable candidates to the current focus, audience, seeds, language, market and domain; `GET /api/keyword-plan` applies the same filter, so the list shows exactly what the generator can offer. PINNED rows always re-enter the rebuild past the scope and coverage pre-filters, so a pin survives a profile change unless the full assessment drops it. PINNED/SKIPPED/USED survive; stale rows are deleted only if still OPEN when the transaction runs. The article and its guarded OPEN/PINNED → USED transition share one transaction; a topic skipped mid-generation leaves the article unlinked (`KEYWORD_PLAN_TOPIC_UNAVAILABLE`) instead of discarding it.
- `scope.ts` `inScope`: one `topicScope` classifier call per batch keeps only items the blog's focus covers, judged by the item text, not by whether the model knows the name. Keyword search finds the category, not the scope (`videohry` returns GTA news to an RPG blog). Errors propagate: callers fail closed.
- News (`news.ts`): Google News via DataForSEO (`/serp/google/news/live/advanced`, $0.002 per query) in the tenant's market. Two OR queries per run, tenant keywords and plan candidates, so a busy plan keyword cannot crowd out the category. Apostrophes and quotes inside a term empty the result, so `newsQuery` strips them. Stories older than 72 h are dropped; the rest go through `inScope` with their snippet and max 5 reach the picker numbered. GDELT was dropped: it rejects short terms (BMW, RPG) and rate-limits an IP for minutes after a burst. Google News RSS forbids commercial use.
- Themes, not pillars, decide rotation. A pillar is only the seed that first suggested a keyword, so `dotace na okna` and `dotace na střechu` could sit in different pillars while the homepage reads as one subject. The assessment labels each topic with a cross-seed `KeywordCluster.theme` (reusing known labels); the picker labels non-plan articles, and `Article.theme` stores the plan's label when a topic was used, so plan and news articles count under one name. `orderCandidates`: pinned first, then score / (1 + 0.6 × repeats of the theme among the last 5 published/draft articles); a theme already at 2 of 5 rests unless its `peakMonth` is ≤ 3 months away or nothing else is left. The penalty is computed at pick time, never stored: `score` is the topic's value, diversity depends on the moment. Topics planned before themes existed fall back to their pillar until the next rebuild. Replaced the old "two from the last pillar, rest after three in a row" rule, which allowed 75 % one-subject feeds.
- Coverage recheck (`recheckCoverage`): rebuilds run monthly, so before offering topics the first 6 OPEN candidates are re-judged by `assessOpportunities` against articles created after their `opportunity.checkedAt` (one call, only when such articles exist). Covered → SKIPPED with `articleId` of the covering article; a gap that article misses → EXPAND suggestion (published only); the rest get a fresh `checkedAt`. A failed check offers the topics unchanged.
- Picker: up to 3 plan candidates (pinned first) and the news list. `topicSchema.planKeyword` adds a `## SEARCH INTENT` writer block and marks the cluster USED. `newsItem` > 0 forces research (no sources = held for review) and adds a `## NEWS HOOK` block; the story URL is stored in `Article.newsUrl`. News is not fetched when 2 of the last 5 articles have a `newsUrl`.
- `CRON_GENERATE_ARTICLE` metadata carries `keywordPlan { offered, chosen, linked }` and `news { queries, found, relevant, used, costUsd }` or `{ skipped }`. UI: sidebar page `/admin/keywords` (`pages/admin/keywords.vue`, `components/Keywords/*`, one shared `useKeywordPlan` query on `/api/keyword-plan`). Header value line and market select, three numbers (search demand of written topics, top-10 share of tracked articles, topics ready), then results and update suggestions (each rendered only when non-empty; the page shows one dashed line for whatever is still pending) and the pin/skip plan: first five topics, the rest and skipped topics collapsed, volume bars relative to the largest topic, difficulty shown only when topics differ. Without AI + ARTICLE_CRONS the page shows only how to enable them; a small information button reveals each topic's reason. PINNED items take priority before the API's display limit and are listed newest first, the order `keywordPlanFor` offers them; load failures are distinct from an empty plan. `tests/eval/keywordScope.test.ts` tests relevance and `keywordOpportunity.test.ts` tests intent, semantic coverage, within-plan duplicates and specific gaps with controlled SERP fixtures; both require `AI_EVAL=1` and write local reports to `tests/eval/.results/`.
- `tests/eval/keywordDiscovery.test.ts` additionally requires `DATAFORSEO_EVAL=1`. It runs the complete discovery pipeline on live Czech Labs/SERP data for coffee, affordable cars and RPG blogs, writing an in-memory plan and a local report instead of touching tenant data. Unlike ordinary unit tests, these opt-in evals incur provider costs.
- `keywordSerps.json` captures real Czech queries and organic results from 2026-10-04 for regression replay (`keywordSerps.test.ts`, AI cost only); assertions reject TV-season and music interpretations outside the tenant's focus. `keywordTopic.test.ts` verifies that an eligible planned query survives the actual topic-selection call instead of drifting to an unrelated idea. Topic selection uses medium reasoning with a 2000-token answer allowance plus middleware headroom; its wire schema accepts the format/module candidates, then the server filters ineligible decorations and validates the complete topic, preserving the search need when one extra module was invalid. SERP lookups run in batches of five; a complete outage, or failed evidence for every surviving recommendation, preserves the previous plan instead of replacing it with unverified topics.
- `rank.ts` claims each due paid check, filters to active ARTICLE_CRONS tenants and schedules from actual `Article.publishedAt`. Rank points store country location, language and domain; results and the difficulty ceiling use only matching measurements. UI exposes the actual ranked URL, because the position belongs to the domain's best page rather than necessarily the linked generated article.
- Article updates (`refresh.ts`, `ContentAction`, `/api/content-actions`, `Keywords/Actions.vue`): REFRESH suggestions need a published page at least 30 days old and two readings on positions 8–20 for that exact article URL; EXPAND suggestions reuse the opportunity assessment when an existing published article can answer an additional reader need. Open suggestions and recent decisions suppress repeats for 60 days. The UI offers preparation, a sanitized preview and a change summary, explicit apply/discard and rollback. Suggestions are free; Premium can prepare 25 updates monthly and Custom 15, for one article credit each. Preparation reserves a credit, queues fresh SERP/research and bounded section edits (at most 40% added or removed words), then settles the credit and READY state in one transaction. Failures release the reservation and do not consume the monthly allowance. A tenant lock serializes allowance checks; a separate `processingUntil` lease prevents duplicate work without changing the billing month. Expired reservations cannot fund new provider work.
- Apply/rollback use the request's policy-enhanced database, tenant and member permissions (AI_USE for preparation, ARTICLE_PUBLISH for apply/rollback, ARTICLE_WRITE_OTHERS for another author's article), and a fingerprint plus guarded transactional writes covering title, excerpt and body. They preserve manual changes made while a proposal waits or while a transaction starts. Section replacements retain existing media and polls. Apply saves the previous content, sources and metrics for rollback, updates reading time and researched sources, and notifies translations, feeds and webhooks. The five-minute `content-actions` task prepares queued edits and measures the exact edited URL for the action query after 30 days, including expansions without a USED keyword cluster; regular rank readings may satisfy the same measurement. This records search position, not clicks or a causal traffic uplift. Migration: `20261004220000_content_actions`; regression tests: `tests/server/keywords/refresh.test.ts`, `contentActionRoutes.test.ts` and PostgreSQL `refresh.integration.test.ts` (`TEST_DATABASE_URL` must identify a separate test database).

### Backlinks (`server/utils/backlinks/`)

- Earned links only. There is no link network, exchange or paid placement: Google treats those as link schemes, and every tenant sharing Topiqu's hosting and templates would make one network trivially detectable, so a single manual action could hit all of them. The page `/admin/backlinks` finds pages that should link, drafts the request and verifies the result; the editor sends the e-mail from their own mailbox. Topiqu never e-mails a third party: cold outreach from SES would put the transactional sender reputation at risk and is regulated commercial communication. Personal e-mail addresses are never collected; the only contact hint is a same-host contact page link found on the source page.
- Plans (`backlinkAllowance` in `shared/utils/backlinks.ts`): PRO gets unlinked mentions and verification; PREMIUM/CUSTOM add manufacturer pages and AI outreach drafts. Discovery also needs the `AI` feature. `BACKLINK_PLANS` gates both tasks.
- When both links and opportunities are empty, `Backlinks/Empty.vue` replaces the two empty lists with one introduction to discovery, outreach and verification. It owns presentation only; the page supplies search availability, running state and refresh timing and handles its search event. The earned-link metric shows its outreach note only for a nonzero count.
- Owned hosts are the blog domain and `ClientSite.websiteUrl` (`ownedHosts`); a link to either, or any subdomain of either, counts. A request asks for a link to the company website when there is one (`backlinkTarget`), because that is the page the business needs authority for.
- Discovery (`discover.ts`) is claimed with `ClientSite.backlinksAttemptedAt` (`claimBacklinkDiscovery`): monthly from the daily `backlink-discovery` task (20 tenants per run), or manually from the page after seven days. The manual route claims before answering, so the page sees `running` immediately and polls; the run itself continues in the background. `backlinksRefreshedAt` is stamped only when at least one source succeeded. Cost per tenant is a few cents: two to three Content Analysis searches ($0.024 + $0.000036/row) and up to five 10-result SERPs; each run logs `BACKLINKS_DISCOVERED` with `costUsd`.
- Unlinked mentions (`mentions.ts`): DataForSEO Content Analysis (`one_per_domain`, 50 rows) for every owned host verbatim and for the tenant name unless a host already spells it. Owned, reference (`isReferenceDomain`: forums, social, encyclopedias, public sector) and spammy (`spam_score` > 30) pages are dropped. Name matches go through one `backlinkMatch` model call, because a name search finds every "Alfa". Up to 25 pages are then fetched: a page linking already becomes a `Backlink`, a page whose text still names the term becomes an opportunity, anything unreadable is skipped. Content Analysis data can be weeks old, so the page itself is always the evidence.
- Manufacturers (`suppliers.ts`): the top five `KnowledgeProduct.brand` values (Heureka `MANUFACTURER`, Google `g:brand`, Shopify `vendor`), excluding the shop's own label, each searched as `<brand> <dealer term>` in the tenant market; one `backlinkMatch` call picks the brand's own dealer page or homepage, never a marketplace or retailer. A listed shop is recorded as a backlink, an unlisted one as an opportunity.
- Pages are read by `page.ts` through `fetchPublicUrl` (SSRF-pinned, https only, so an http URL is upgraded; 3 MB cap; charset from header or meta). `readPage` returns links to owned hosts with `rel` and anchor, followed links first. `gone` (404/410) counts against a link, `failed` (blocked, timeout, 5xx) does not.
- `BacklinkOpportunity` statuses: OPEN → SENT (editor clicked "sent", first check in a week) → WON (link verified) or EXPIRED (no link 60 days after sending); OPEN/SENT → DISMISSED; DISMISSED/EXPIRED → OPEN. Rediscovery refreshes the evidence of an OPEN row only and never reopens a decision. Writes use guarded `updateMany` on the expected status; a lost race is a 409.
- Verification (`check.ts`, daily `backlink-check`): SENT requests weekly; verified `Backlink` rows weekly, with a miss re-read the next day and the link marked lost after `BACKLINK_LOST_AFTER` (2) misses in a row. A page that cannot be read keeps its link until it has not been seen for 30 days. Both loops claim each row by its `nextCheckAt` before fetching.
- `Backlink` has only a read policy: rows are created by system code after the page was actually fetched, never by a client. Routes (`/api/backlinks`, `/discover`, `/[id]`) use `ANALYTICS_READ`, like AI visibility; drafts additionally need `AI_USE` and are rate-limited (30/h per tenant), manual checks 20/h. Draft input is untrusted page data and the model may only write text.
- Outreach drafts (`outreach.ts`, `backlinkOutreach`) are written in the source page's language, at most ~120 words, and must never offer money, a reciprocal link or a guest post. The UI offers copy and `mailto:` without a recipient.
- Tests: `tests/unit/backlinks.test.ts` (hosts, allowance, matching), `tests/server/backlinks/*` (page parsing, mention filtering, discovery persistence, verification and lost links, route authorization). Migration `20261007120000_backlinks`; adding `brand` to the hashed feed facts makes every feed sync once as changed without re-embedding, which fills the column.

### Knowledge (first-party RAG)

- `KnowledgeSource` (`prisma/models/knowledge.zmodel`) holds a tenant's note / file / URL as **extracted text only**; uploaded files are never stored, because the S3 bucket is public behind the CDN. `KnowledgeChunk` carries `embedding vector(1536)` (pgvector) and a generated `searchVector` tsvector over `knowledge_unaccent(content)`. **Postgres must ship pgvector** — `pgvector/pgvector:pg18-trixie` locally, in CI and in production (same major version and Debian base as the former plain `postgres:18`); on a plain image the migration fails.
- Pipeline: `/api/knowledge` (TENANT_SETTINGS scope, AI plan) → `knowledge/extract.ts` (magic bytes must match the extension; `unpdf`, `mammoth`, `fetchPublicUrl` for URLs; HTML goes through `extractReadableSource` in `factCheckSources.ts`, shared with fact-check, which renders `<del>/<s>/<strike>` and `<ins>` as `[deleted: …]` / `[inserted: …]` so legislative redlines don't merge both wordings; `ai/factCheck.ts` accepts a side as in force only when the page says so) → row `PENDING` → `knowledge/indexing.ts` (heading-aware chunks prefixed with title › heading path, `embedMany`, atomic claim; old chunks replaced in the same transaction that marks `INDEXED`). `knowledge-index` cron (every 5 min) is the safety net behind the immediate kick; `PROCESSING` older than 10 min is reclaimed, 3 attempts then `FAILED`. An edit bumps `version`, so an in-flight run for older text cannot mark the source indexed.
- Retrieval (`knowledge/retrieve.ts`) runs beside `researchTopic` in `buildArticleConfig`: embed → one SQL with semantic + OR-tsquery lexical ranks fused by RRF → similarity floor 0.2 (the top 5 lexical hits are exempt, so a plan name or code the vector misses survives), ≤3 chunks per source, top 15 → `knowledgeSelect` model gate, which may return nothing (ranks cannot say "unrelated"). No tenant with indexed sources = no model call. The query is `knowledgeQuery` — the manual prompt, or the cron topic — so knowledge still applies with web research off. Selection bumps `usageCount`/`lastUsedAt`; the playground (`POST /api/knowledge/test`) passes `track: false`.
- Lexical terms are folded in SQL by the index's own `knowledge_unaccent`, never in JS: NFD misses what unaccent rewrites (ł → l, ß → ss). Stopwords come from the tenant's corpus, not per-language lists: above 50 chunks a term in >30 % of them is dropped, the rarest always stays. Only chunks embedded by the current `aiEmbeddingModelId` are searched, so a model switch hides not-yet-reembedded sources instead of comparing incompatible vectors.
- The editor's generation result lists the knowledge sources used (`research.knowledgeSources`), each linking to `/admin/knowledge?source=<id>`, which opens that source.
- **Retrieval changes are measured, not eyeballed:** `bun run knowledge:eval` (`scripts/knowledge-eval.ts` + `scripts/fixtures/knowledge-eval.json`) indexes a fixture corpus into `TEST_DATABASE_URL` with the real models and fails below recall 0.9 / precision 0.8 / abstention 0.9. It also reports recall@3/10 and MRR of the shortlist before the gate, so a miss is attributable to retrieval or to selection, and scores `indirect` cases (topics that never name what the source covers) apart, ungated. `expect` must be selected, `allow` may be (pricing in a comparison). Tightening the gate prompt moved precision from 0.73 to ~0.87.
- Freshness: the brief dates each entry by `knowledgeAsOf` (`validAsOf` → `fetchedAt` → `indexedAt`) and marks it `STALE` in code past 12 months, so the verifier never does date arithmetic. `validAsOf` is filled from PDF `ModDate`/`CreationDate` or HTML publish date, editable in the UI. `knowledge-refresh` (hourly, 50 URLs per run) re-fetches URL sources older than 7 days and queues feeds older than 24 h: unchanged text only moves `fetchedAt`; changed text becomes a new version; a failed fetch keeps the last good index and records `error`. The same run requeues sources whose `embeddingModel` is no longer the registry's.
- Quotas per plan in `shared/utils/knowledge.ts` (`knowledgeQuota`); create/refresh/playground are rate-limited per tenant and per IP (`consumeRateLimit`). Knowledge model costs (embeddings, gate) are logged, not charged: indexing via `KNOWLEDGE_SOURCE_INDEXED`, playground via `KNOWLEDGE_TEST_QUERY`; in articles they join `researchTokens`.
- Sitemap import: `POST /api/knowledge/sitemap` only discovers pages (same site, https, one sitemap-index level, capped by `maxSitemapPages` and remaining quota) and the dialog shows found / already known / offered with the cap reason before anything is imported; the client adds them two at a time through the regular URL create, so extraction, SSRF pinning, dedupe, quotas and the 60/h create limit apply unchanged. For website addresses, `knowledge/sitemap.ts` reads up to 512 KiB of `robots.txt`, tries at most five unique same-site HTTPS `Sitemap:` declarations, then falls back to `/sitemap.xml`; an explicit XML URL skips discovery. The first successfully fetched sitemap is used. Redirects stay within the same host family (`www` and bare host are equivalent), with public-address validation and DNS pinning at every hop.
- Company website onboarding: the sibling landing forwards optional `websiteUrl` and versioned processing confirmation through its signed checkout request. The platform creates `WebsiteImport` only inside the account-creation transaction; there is no manual start endpoint. `server/utils/websiteImport` runs immediately in the background, with the minute `website-import` task as its recovery path. Atomic database claims prevent duplicate execution across replicas. One Anthropic request allows at most two domain-restricted searches; one subsequent structured extraction has no tools. Both disable thinking and automatic provider retries. Up to five HTML pages (2 MiB / 12,000 characters each) use the existing DNS-pinned fetcher with same-domain redirects. Metadata supplies observed brand assets, primary color and social links; unsupported assets remain missing. Existing knowledge rows are deduplicated and created with `useInArticles: false` under an atomic tenant quota check. The notice, checklist and settings panel share one client polling scope through `useWebsiteImport`; stale reads are cancelled and its cached handler releases component state on disposal. The persistent `Admin/WebsiteImportNotice.vue` opens `WebsiteImport/Panel.vue` in settings: review/edit and select fields, accept all available values, or skip. Applying uses the request-scoped policy client, checks current field hashes and tenant permissions, copies accepted raster assets through existing moderation/storage, enables only accepted import knowledge and records the review. Existing manual knowledge tools remain available for other sources and older onboarding clients.
  `NUXT_WEBSITE_IMPORT_DAILY_BUDGET_USD` defaults to USD 100 globally. A transaction with a database advisory lock reserves USD 4 before dispatch, then settles known model/search usage plus USD 0.10 for bounded knowledge indexing. A depleted budget defers work; unknown provider outcomes retain the reservation and never retry that paid stage. Search checkpoints permit recovery without another search. Migration `20261022140000_website_import` adds the import table, active-tenant uniqueness and nullable `KnowledgeSource.websiteImportId`. Deploy the migration before the app, then the landing confirmation change; older clients continue storing the website without starting AI work.
- **Publish confirmation is enforced server-side**: `POST /api/knowledge` and a note text change in `PATCH` return 400 `KNOWLEDGE_CONSENT` without `confirmed`, and the audit row records `consent: { version: KNOWLEDGE_CONSENT_VERSION, confirmedAt }`. Bump the version when the checkbox wording changes. The add dialog has no "use in articles" switch: everything added may reach a published article, and embedding sends it to OpenAI regardless, so an "unused" upload would only store and ship data. `useInArticles` survives as pause/resume in the list; retrieval (`eligible` and the availability check) is the only path to the writer, gate and verifier, and both filter it.
- **Product feeds** (`kind: FEED`, `knowledge/feed.ts`): an e-shop catalog is one source, not a page per product. The index queue runs the sync (`syncFeed` in `indexing.ts`): stream the XML (`htmlparser2`, no DTD, so no XXE/entity expansion; `maxFeedBytes`) → Heureka `SHOPITEM` or Google Merchant `item`/`entry` adapters → `normalizeVariant` (the only cleanup: HTML → text, https product links without tracking params, ISO 4217 currency, unambiguous prices or `null`) → variants merged by `item_group_id` (lowest price, best availability). One `KnowledgeProduct` row + one chunk per product; price and availability are never embedded, so a price change is an UPDATE and only products whose `textHash` changed are re-embedded, in committed batches. A failed sync keeps the last good catalog; a feed that parses to nothing throws instead of wiping it.
  - Retrieval treats a feed as eligible in any status (chunks are swapped per product, never half-written), only for articles in the feed's `language`, never out-of-stock products. The per-source cap is per product. The brief adds `product · from <price> · <availability>`, formatted in code; the product URL is the citable link, the feed URL never is (it often carries an access token, so the title defaults to its host). The writer states a price only for buying/pricing/comparison topics.
  - `POST /api/knowledge/feed` checks a link before it is added (count, sample, what fits the quota; nothing stored). A failed sync stores a `KNOWLEDGE_FEED_ERRORS` code the list translates; only `unreachable` and unexpected errors are retried, and only unexpected ones reach Sentry.
  - Heureka prices carry no currency, so the feed stores one; `ClientSite.currency` is the billing currency and must not stand in. Product quota is per tenant across feeds (`maxProducts`).
- Manual generation can skip knowledge (`options.useKnowledge`, default on). Audits carry `knowledgeShortlisted` and `knowledgeSelected` (chunks), so the gate's empty-selection rate is measurable per tenant.
- **Raw SQL is the only tenant isolation for chunks** (policies deny the ORM path entirely); `clientSiteId` comes from the session or tenant row, never the request. Deliberately **no HNSW index**: an ANN index filters by tenant after the search and starves small tenants; per-tenant exact scans are cheap. Revisit with pgvector ≥0.8 `hnsw.iterative_scan` once one tenant exceeds ~50k chunks.
- Citations: internal entries reach the writer as `[Kn] … internal` with no URL; only `publicUrl`s join `citationAllowlist`, which replaces the research brief as the input to `filterResearchSources`. The reviewer/verifier receives the brief too: first-party claims about the publisher count as supported, except time-sensitive claims resting on entries older than 12 months or contradicted by an official web source (reported as UNSUPPORTED MATERIAL). Used `{ sourceId, version, chunkIds }` land in the manual `MANUAL_GENERATION_WRITER_STARTED` audit and the cron generation audit.
- Why a claim survived review: `editorialReview.verification` in the generation audit holds every verdict line of each verification round (`verdictLines` in `articleQuality.ts`), not `verificationBrief`, which keeps only URL-backed lines and so drops UNSUPPORTED and first-party-supported verdicts.

### Notifications delivery

- **Email unsubscribe is a signed link, not an address.** `server/utils/unsubscribe.ts` HMACs the user id with `AUTH_SECRET` (non-expiring, so old mails keep working); `pages/unsubscribe.vue` posts it to `POST /api/users/unsubscribe`, which only ever sets `allowEmail = false`. The page acts on a click, not on load, so link-prefetching mail scanners cannot unsubscribe anyone. Verification-code mails are transactional and carry no unsubscribe link.

- Notifications are persisted in the DB (source of truth) and delivered to the client by **polling**, not push. The client (`Notification/Bar.vue`) polls `GET /api/notifications/poll?since=<ISO cursor>` every 10s (paused while the tab is hidden) and merges anything newer.
- Publication notifications share `server/utils/articleNotifications.ts → notifyArticlePublished` across manual publication, scheduled release and cron generation. It uses the actual author's username, recipient language with an English fallback, one translator per language, and follower inserts in batches of 100. The caller supplies its policy-aware DB/transaction and chooses whether to notify the author; cron generation skips the AI author. The unused cron SSE hooks have been removed.
- Notifications related to an article include its `imageUrl`; `Notification/Bar.vue` renders a compact, linked cover for publication, like and comment notifications when one exists. The title is clamped inside the link so its rounded focus outline cannot clip the first letter. Both the paginated endpoint and polling select title, slug, language and image URL.
- Notification messages are stored in the recipient's account language at creation time; changing the interface language does not translate historical text. The language menu saves a differing account preference even when that language already matches the current route.
- Reactions accept published articles and the signed-in author's own drafts. The route keeps deleted articles/sites excluded, uses the policy-aware database client, and suppresses self-notifications; guests and other readers cannot like private drafts.
- Community-insight emotion identifiers come from `shared/utils/communityInsight.ts` and are translated at display time, including `curiosity`. The generated insight schema uses that vocabulary; historical unknown identifiers are omitted rather than exposed as raw labels.
- `Article/Series.vue` uses the cover URLs returned in the article detail's series payload: compact thumbnails identify every entry in the expandable list, while the previous/next cards show wider covers and a two-line excerpt.
- The article editor's leave guard compares `articleEditorSnapshot` values containing only persisted form inputs, tags and the selected series. API-derived fields such as counters and expanded relations cannot create a false dirty state after save or publish.
- This replaced an in-memory SSE channel (`server/utils/realtime.ts` + `/api/notifications/sse` + the `useRealtime` composable), which is unviable on serverless/Vercel: held connections incur per-request/wall-clock billing and isolated function memory means a `publish` in one function never reaches a subscriber in another. That whole layer was removed; reviving push would mean a managed WebSocket provider (Ably/Pusher) or a long-running process off Vercel, not a serverless patch. Cursor semantics live in `server/utils/notificationsPoll.ts` and are unit-tested.
- **That constraint is gone** — the app now runs as a persistent process on its own box (§1), so SSE is viable again and the removed layer is the reference design for bringing it back. Polling is simply what still ships. One caveat before it returns: in-process pub/sub only works at one replica; more than one needs fan-out through Redis/Valkey, which ties into the same "1 vs N replicas" decision as the crons (§8).

### Blog statistics (`/api/stats/dashboard`)

- The dashboard is the only statistics endpoint. The eleven disconnected per-metric routes were removed after checking app, server, scripts, tests and integration documentation for callers; production request logs were not available locally.

- **Saved time / money are derived on read.** One formula in `shared/utils/savings.ts → writingSavings` (`tests/unit/savings.test.ts`): words ÷ speed = hours, hours × rate = money. The dashboard sums `totalWords` over `aiInvolvement: 'FULL'` only (the editor demotes to `ASSIST` on the first human edit) and prices it with the tenant's _current_ rate. `Article.savedAmount` / `savedTimeMinutes` are still written but no longer authoritative — they froze a rate at generation time, so a correction never reached existing articles. Drop them in a later migration; don't add readers.
- **`clients/[id]` PATCH gets `linkedinMode` on every save**, because the settings form defaults it — so that branch runs for tenants who never connected LinkedIn. It must not create a `LinkedinCompany`: only the OAuth callback has a real `linkedinOrgId`, and the stub value it used instead collided on the unique index, 500-ing settings for every tenant after the first.
- **The rate is USD and the column name says so.** `humanHourlyRate` held a CZK figure while the UI formatted it as the tenant's `currency` (default USD), inflating the number ~23×. Migration `20260808120000_human_rate_usd` renames it to `humanHourlyRateUsd`; display multiplies by `useCurrencyRate` like `Billing.vue` / `AI.vue`. The default (35) is stated twice — `client.zmodel` and `DEFAULT_HOURLY_RATE_USD` — so changing it takes both plus a migration that moves rows off the old value, or tenants stay priced at it forever.
- **Admin sidebar** (`Sidebar.vue`): groups separated by dividers (Web, overview and statistics; content; reach; settings). Writing is a button, not a list item. On the publication's canonical origin, Web is a normal same-tab navigation item: `publicationNavigationUrl` returns the current localized index path. From the central host, Open site is an external footer link in a new tab to the verified publication URL in its primary language. Exact matching distinguishes Web and Dashboard; Nuxt routing preserves editor leave guards. The authorized sidebar remains on public routes, while foreign-tenant access stays hidden by the existing host/session gate. Both desktop and teleported mobile sidebar surfaces scope the admin primary/action tokens so publication accents do not change their controls. Header branding follows the resolved tenant on both admin and public pages and links to its index. On the central host Topiqu links to the role's dashboard (or sign-in for other visitors). Widget previews retain their resolved tenant branding. Tags are managed from the article table; custom emoji from the comment emoji picker (tenant admins on their own blog, Pro+) and Settings → Community.
- **`Stats/Dashboard.vue` (page `/admin/stats`) uses neutral report sections.** Sections (`Stats/SectionHeading.vue`) and repeated rows (`Stats/Row.vue` — rank/icon, truncating label, right-aligned metric, optional share bar) share the dashboard's semantic colours. Charts and AI-involvement indicators use neutral tones; status colours remain available for real warnings/errors. `Charts` is behind `<LazyCharts>` so chart.js stays out of the chunk for BASIC, which never renders it.
- **Truncation needs `min-w-0`.** A flex item defaults to `min-width: auto` and refuses to shrink below its content, so a long tag name pushed the view count out of its container. Every truncating label on this page sits in a `min-w-0` parent with a `shrink-0` metric beside it.
- **`Modal/index.vue` had no dark tokens at all** — a white panel in dark mode, with the one card that _did_ carry `dark:` variants floating in it. The panel and its title gradients now have them. `h-11/12` is untouched and still forces every modal to ~92% viewport height regardless of content.
- **`Charts.vue` takes semantics, not a Chart.js config** — `kind` (`trend` bar↔line / `breakdown` bar↔pie), `labels`, `values`; it owns colours and scales. Canvas colours are resolved from rendered semantic text/border/background tokens and update with colour mode. Bar/line charts use one neutral tone; pies use stable category tones, readable labels and a table alternative. `Stats/Dashboard.vue` always sends all five share platforms including zeros, since dropping the empty ones would repaint the survivors.
- **A share is gated per identity per platform**, the same way `ArticleReaction` gates a like: `ArticleShare` carries `userId`/`sessionId` (the client fingerprint for anonymous visitors) and the handler skips the increment when a row already exists. The unique index is only a backstop — every row carries a NULL in the tuple, and Postgres treats NULLs as distinct, so it catches nothing on its own. Every share button goes through `composables/useArticleShare.ts`, which adds the fingerprint for anonymous visitors (without it the POST is a 400). `Article/TOC.vue` only emits `share` up through `Article/View.vue`, so the editor preview never counts one.
- **`ArticleView` is the view-event log** (migration `20260819120000_article_view_events`); `Article.views` stays the running counter, so sorting and totals keep their fast path. One row per visitor per article per UTC day, and `sessionId` is **non-nullable** precisely so the unique index bites — `ArticleShare`'s equivalent index catches nothing because every row carries a NULL in the tuple. `view.post.ts` inserts with `ON CONFLICT DO NOTHING` and increments the counter **only when a row was actually written**, so the two never drift. Consequences: the counter now means _unique visitor-days_, not raw hits, so it grows slower than the historical values above it; the series cannot be backfilled, hence `trackingSince` (NULL until the first event) which the client renders as "měřeno od …" instead of drawing flat zeros.
- **The daily series is real readership now**, bucketed on `ArticleView.viewedOn` over `VIEW_TREND_DAYS` (30). It replaced a 7-day series bucketed by `COALESCE(publishedAt, createdAt)`, which counted views accumulated by articles _published_ that day — not views that happened that day.
- **Views were forgeable.** `view.post.ts` had no session, no dedup, no rate limit and no `status` filter: a loop of `curl` moved the number, and an admin previewing a draft inflated it. The identity is now server-issued (the `anon_session` cookie, never read from the body) and drafts are rejected. Totals and `topArticle` filter `status: 'published'` for the same reason.
- **Engagement is a site-wide ratio**, `interactions ÷ views` (`server/utils/dashboardStats.ts`, `tests/unit/dashboardStats.test.ts`). It used to be the _mean of per-article ratios_, which let a 1-view article with 3 comments contribute 300% — that is why the client clamped the display at 100%. The clamp is gone; do not reintroduce it to "fix" a number above 100%, fix the formula.
- **`topTags` ranks in SQL.** Prisma cannot order a tag by an aggregate over its articles, so the old code took the 10 tags with the most articles and sorted _those_ by views — a tag riding two heavily-read articles never entered the candidate set. The raw query joins and `ORDER BY SUM(views)`. Note the metric double-counts by design: an article with three tags gives its views to all three.

### Domains

- `DomainConnection` reserves custom hosts and owns provider IDs, encrypted queued certificate material, lifecycle and reconciliation leases. Generic model writes are denied; tenant-settings routes authorize system provisioning. `server/utils/domains/` contains provider boundaries, certificate validation, signed routing probes and reconciliation; the existing domain task retries setup/cleanup and rechecks ownership. GET uses an explicit safe projection. Managed-domain switches stay local. See `docs/custom-domains.md` for rollout, O2O, manual-resource attachment, certificate limits and platform-host administration.
- Disconnect/cancel first commits the safe address change and cleanup request, then attempts cleanup under a fresh lease. Retired connections can be retried by their tenant-scoped ID even after the canonical host has changed. A cleanup-only attempt cannot provision a subsequently reused connection. No-resource cleanup is local; provider failures retain IDs for retry. This tenant's pending cleanup is reported separately from another tenant's reservation.
- Domain settings separate ownership, HTTPS and activation. The scoped domain GET reconstructs permanent DNS instructions for every retained connection without exposing provider credentials or raw connection rows. `shared/utils/domainRecords.ts` retains exact Cloudflare challenges in the existing JSON field, marks current requirements separately from history, and keeps multiple TXT values at one name. The UI offers activation only after READY, retains DNS instructions after activation and opens replacement-address setup explicitly.

- DNS verification explicitly requests JSON parsing for Cloudflare's `application/dns-json` responses; ofetch otherwise returns a Blob, hiding the DNS status and records. This shared lookup serves initial verification, domain switches and scheduled revalidation, retaining exact TXT challenge and normalized CNAME matching.
- `domainError` (`shared/utils/domain.ts`) is the one claim rule: a managed host must be a single unreserved label under the base domain (managed hosts are auto-verified, so `billing.topiqu.com` would be a live platform host), and a custom domain needs a non-BASIC plan. `isDomainTaken` (`server/utils/domainVerification.ts`) also counts old hosts in `DomainRedirect`, so nobody can take over another blog's redirect. Onboarding, tenant creation and the availability check all go through both.
- `domain` is superadmin-only in `PATCH /api/clients/[id]`. A tenant moves through `/api/domain/pending`: the new domain is stored as `pendingDomain` with its own TXT token while `domain` keeps serving; `pending/verify` checks TXT + CNAME and then, in one transaction, swaps the two, adopts the token for `domain-reverification` and writes a `DomainRedirect` for the old host. A direct swap would take the blog offline, because `tenantByHost` refuses an unverified custom domain. Settings → Branding → `Form/Client/Domain.vue`.
- `server/middleware/domainRedirect.ts` answers an old host with 301 (308 for non-GET) to the current domain, path and query kept. It only looks up redirects when the host is not a live tenant, and the swap drops the cached host lookups for both hosts (`uncache`).

### Integration OAuth and billing returns

LinkedIn and Search Console connections can start from an authorized tenant host,
including its verified custom domain, or the central app. The source POST creates a
hashed, expiring grant bound to the initiating account, session, tenant, exact origin
and locale. `/integrations-connect` on the central auth origin explicitly confirms
that account before starting provider OAuth. The callback rechecks source-session
validity and tenant capabilities and atomically consumes the grant.

  uses HttpOnly, host-only cookies with the `__Host-` prefix under HTTPS. Both the
  provider authorization and its callback use the central origin; neither login
  handoffs nor shared subdomain cookies transfer integration state.
- **Returns preserve the verified source origin and locale.** Integration returns
  use the origin and supported locale captured by the grant. Stripe checkout,

  codes, tokens, grant values and raw provider errors must not enter telemetry.

### External API

> **`docs/external-api.md` is the consumer-facing spec** — auth, envelope, per-endpoint field
> tables, error table, enums, and the pagination/deletion/HTML-rendering recipes an integrator
> needs. This section stays the architectural note; that file is what a third party reads. A
> change to any `server/api/external/*` response shape has to land in both.

- Every external route authenticates through `server/utils/externalApi.ts → requireExternalClient` using the tenant's `x-api-key`; soft-deleted sites are refused and authenticated responses are `private, no-store`. An admin generates or rotates the single key through `POST /api/clients/[id]/api-key`; rotation immediately invalidates the previous key. The key is stored on `ClientSite` and is visible to the owning tenant in Settings → Integrations.
- `GET /api/external/articles` remains the backwards-compatible collection endpoint. It returns **source-language, published `Article` rows only**, newest first. Its original fields and nested `tags[].tag` shape remain intact; additive fields now expose `updatedAt`, `publishedAt`, reading time/word count, sources, cover credit, series and metadata for published translations. Pagination is `page` + `limit` (defaults 1/10, maximum 100), and response metadata includes the primary language and applied tag filters. Optional comma-separated `tag` filtering is trimmed/deduplicated and retains **AND semantics**: an article must carry every requested tag slug.
- `GET /api/external/articles/:id` returns one published tenant article with the complete safe external projection. Its response uses flat `tags`, identifies the source `language`, and exposes published translation summaries as `availableTranslations`; a foreign, draft, archived or missing id is the same 404.
- `GET /api/external/tags` is discovery for filtering: only tags actually attached to at least one published article of the authenticated tenant, sorted by name, with `articleCount`. This deliberately avoids leaking global/other-tenant tags and omits empty tags.
- `GET /api/external/site` returns public integration metadata (`name`, domain, description, logo, theme, primary/available languages, socials) plus the published article count; it never projects billing, AI configuration or credentials.
- This remains a read-only pull API; change propagation is pushed by webhooks (below). There is no change/deletion cursor, conditional request support, localized full article response, canonical public URL, key scopes, per-integration keys, rate-limit contract, OpenAPI document or URL version namespace. Those require a deliberate v1 contract and, for reliable unpublish/delete propagation, a persisted change log rather than inference from the current published collection.

### Webhooks (`server/utils/webhooks.ts`)

- Pro+ tenants register up to `MAX_WEBHOOKS` HTTPS endpoints (Settings → Integrations, `/api/webhooks`, `INTEGRATION_CONTROL` scope) for `article.published` / `updated` / `unpublished` / `deleted` on the source-language article. Published/updated payloads reuse the External API projection plus the public `url`; removals carry only `id`/`slug`/`language`, because a deleted row is gone by delivery time.
- `enqueueArticleWebhook` writes one `WebhookDelivery` outbox row per endpoint with the payload frozen at enqueue time, then tries to send at once; `webhook-deliver` (every minute) retries after 1/5/30/120/720 min and prunes rows older than 30 days. Every publication path calls it (create, PATCH, delete, `publish-check`, `generate-article`, SEO autopilot write + rollback); a new path that changes a live article must too. Enqueue never throws into the article write.
- A claim is a guarded `updateMany` to `SENDING` whose `nextAttemptAt` doubles as a 5-minute lease, so overlapping runs never double-send and a crashed send is retried (at-least-once; receivers dedupe on `Topiqu-Delivery`).
- `Topiqu-Signature: t=<unix>,v1=<hmac-sha256(secret, "t.body")>`. The secret is `@omit`, returned only on create/rotate. Sends go through `postPublicUrl` (DNS-pinned, private ranges refused, redirects not followed) because the URL is tenant input. 20 consecutive failures switch an endpoint off (`disabledAt`); re-enabling resets the streak.

### Site widgets (`shared/utils/widgets.ts`)

- Deleting from a widget card or its editor uses the shared `useConfirm` dialog with the widget's title. Approval removes the draft by its stable key; the existing Save action persists the change. Cancel leaves the widget and editor intact.
- `SiteWidget` rows (Settings → Widgets, `GET`/`PUT /api/widgets`, `TENANT_SETTINGS` scope). `PUT` replaces the tenant's whole set in one transaction; array order is `position`, and a body id that is not one of the tenant's live rows becomes a new row. Widgets left out are soft-deleted (`deletedAt`), and the audit entry lists their ids and kinds. `config` is Json validated per `kind`.
- `slot` is a string key of `WIDGET_SLOTS`, not an enum. The layout owns the slots; when a redesign drops one, map it in `RETIRED_SLOTS` so its widgets move, and `resolveWidgetSlot` skips anything unknown. Pages render a slot with `<WidgetSlot name>`: `HOME_TOP` / `HOME_MIDDLE` / `HOME_BOTTOM` in `pages/index.vue`, `ARTICLE_END` in the article footer, `FOOTER` in the layout. At most `MAX_PER_SLOT` active widgets each.
- Active widgets ride in `publicClientSiteSelect`, so rendering costs no extra request. Both routes that return it pass them through `publicWidgets`, which drops kinds the plan lacks and strips the HTML body. Plan limits apply at render, not on `PUT`, so a downgraded tenant keeps and can still save its widgets.
- `ANNOUNCEMENT` (all plans) renders as `Widget/Bar.vue` above the content, only on the publication shell. Time windows are evaluated at render, not stored as state. `widgetsInputSchema` refuses two active bars that share a language and overlap in time. Closing writes `announcementKey` (id plus a hash of text and link) to the `topiqu_bar` cookie, read during SSR, so a closed bar is never rendered and an edited one shows again.
- `DIVIDER`, `CTA`, `PRICE`, `WEATHER` need Pro+. A CTA image is a `MediaAsset` id; `PUT` checks the asset belongs to the tenant and writes its URL itself.
- `PRICE` and `WEATHER` load client-side from `/api/widgets/:id/data`, which reads the stored config, so it is no open proxy. Providers (`server/utils/widgetData.ts`) are keyless and cached in Redis: Frankfurter/ECB for fiat (1 h), Coinbase exchange rates for crypto (5 min), MET Norway forecasts (30 min, coordinates rounded to 4 decimals). Forecast days follow the place's mean solar time (`round(lon / 15)` hours), not UTC; with no timezone database, a day boundary can be off by an hour or two (DST, political zones). The day's symbol is the six-hour summary nearest local noon. MET and Nominatim (the editor's place search, rate-limited per tenant) require the identifying User-Agent.
- `HTML` needs Pro+ and a verified own domain: on `*.topiqu.com` a hostile script would put the platform domain's reputation at risk. The page never receives the body; `<WidgetHtml>` frames `/widgets/:id` (`server/routes/widgets/[id].get.ts`), which serves only on the tenant's own host, with `CSP: sandbox` minus `allow-same-origin`. The header, not just the iframe attribute, is what keeps the document opaque when opened directly. `routeRules` turns the global security headers off for `/widgets/**`, since its CSP would block the tenant's scripts. The frame reports its height by `postMessage`; the parent checks `event.source` (the origin is `"null"`) and clamps it. `server/middleware/opaqueOrigin.ts` refuses cookie-carrying API writes with `Origin: null`.
- Editor (`Form/Client/Widgets.vue`) groups widgets by slot, with the active count against `MAX_PER_SLOT`; arrows swap neighbours within a slot, and a widget moved to another slot goes to its end. A failed save names the widget by kind and slot, highlights and focuses its card. `PRICE`/`WEATHER` preview live data before saving via `POST /api/widgets/preview` (`TENANT_SETTINGS`, plan-checked, 30/min per tenant, same providers and cache); `Widget/Price.vue` and `Widget/Weather.vue` take that as a `data` prop instead of fetching. `HTML` has no inline preview: a `srcdoc` frame would inherit the admin CSP and block the tenant's external scripts, so the editor links to the saved, active widget's frame on the tenant's own domain instead.

## 6. Data Model

- Authored in ZenStack, **split by domain**: a thin root `prisma/schema.zmodel` (datasource/policy plugin + `import`s) pulls in `prisma/models/*.zmodel` (`base`, `article`, `poll`, `client`, `user`, `comment`, `notification`, `linkedin`, `log`). Enums colocate with their domain; cross-domain enums + reusable `Base`/`Ownable` types live in `base.zmodel`. `bun zenstack:generate` writes the runtime schema and TypeScript types to ignored `generated/zenstack/`; `shared/databaseSchemas.ts` derives server-side Zod v4 model validators from the same metadata. Browser-used language/theme schemas live in `shared/siteSchemas.ts` so the 320 kB runtime metadata stays out of client chunks; `tests/unit/siteSchemas.test.ts` pins those option lists to the generated enums. Imports must be at the top of each file; cross-file relations need explicit `import`s (ZenStack resolves symbols only over a file's transitive imports).
- Migrations in `prisma/migrations/`.
- `bun build` pipeline: `zen generate` → `nuxt build`. Releases apply existing SQL migrations separately with `bun db:migrate:deploy` (`zen migrate deploy`).

### Polls

- `ArticleView` is the only event table with a **non-nullable identity column** (`sessionId`). That is deliberate: `ArticleShare`, `ArticleReaction` and `ArticleFeedback` all put nullable `userId`/`sessionId` in their `@@unique`, and Postgres treats NULLs as distinct, so those indexes never fire and the handlers carry the dedup alone. Copy `ArticleView`'s shape, not theirs.
- Fully normalized: `Poll` (question, order) → `PollOption` (label, order) → `PollResult` (vote). All cascade-delete from `Article`. `PollResult` references both `Poll` and the chosen `PollOption` by **real FK** (+ `articleId` kept denormalized so engagement stats use `Article._count.pollResults`). Two `@@unique` constraints — `(pollId, userId)` and `(pollId, sessionId)` — enforce one vote per identity at the DB layer.
- Poll blocks are authored as Tiptap nodes (`extensions/poll.ts` + `extensions/Poll.vue`) and serialized into `Article.content` as `<div data-type="poll" data-poll-id data-question data-options>`, where `data-options` is a JSON array of `{ id, label }`.
- On article create/edit, `server/utils/articlePolls.ts → syncArticlePolls` reconciles the embedded blocks with the `Poll`/`PollOption` rows and stamps each block with server-assigned ids (poll id on the block, option ids inside `data-options`). Question/labels stay mirrored in the HTML so the editor round-trips and client rendering needs no DB read; the DB holds the stable ids votes key off. Option/label normalization lives in `shared/utils/polls.ts` (`normalizePollOptions`).
- **`syncArticlePolls` is mandatory on every write path that persists `Article.content`** — it is the only code that creates `Poll`/`PollOption` rows _and_ the only code that mints the ids the vote endpoints key off, so skipping it yields a poll that is unvotable in both directions at once. `finalizeArticle` emits only a cosmetic `data-id` and label-only options, so the `generate-article` cron (which writes AI output straight to the row) must run the same sync + `sanitizeHtml` as `articles/index.post.ts` and `[id]/index.patch.ts`; it previously did neither, shipping polls whose every click was a silent no-op (`Poll.vue` bails before `$fetch` on a missing option id, and the GET counts endpoint happily returns an empty tally for an unknown `pollId`, so the widget looked live). `scripts/backfill-polls.ts` repairs rows written before the fix (dry-run by default, `APPLY=1` to write). Covered by `tests/server/articles/articlePolls.test.ts`.
- **The editor rewrites `data-options` on every keystroke** (`Tiptap/Editor.vue → validateContent`, fed by `onChange`), so that pass must round-trip the option ids and be idempotent. It went through `shared/utils/polls.ts → pollOptionsAttr` (`tests/unit/polls.test.ts`) instead of an inline `String(x)` that assumed the legacy `string[]` shape — that wrote `[object Object]` over every label and dropped the ids, which `Poll.vue` then rendered as unvotable buttons at 0%. It hit any poll opened in an editor, most visibly the **translation reviewer**, since a translated article is edited there far more often than the source is re-saved.
- Votes key off **`optionId`** (not the label text), so renaming an option never splits counts and removing one cleans up its votes via cascade. Vote endpoints: `server/api/articles/[id]/vote.ts` (GET counts via `groupBy`) + `vote.post.ts` (cast; maps PostgreSQL unique violation `23505` to 409).
- Render: `Article/Parsed.vue` (client-side parse) → `Article/Poll.vue` (votes by `optionId`); homepage "latest poll" via `extractPollData` in `by-clientsite/[slug].ts`. Both require `data-poll-id` and **do not** fall back to `data-id`: that attribute is cosmetic, never a vote target, and the fallback's only effect was to render a dead widget instead of surfacing the missing sync.
- **Legacy note:** the `20260527130000_polls_normalized` migration wipes any pre-existing `PollResult` rows (old text-based votes couldn't be remapped to option ids without parsing HTML) — a one-time, intentional reset.

### Article Translations

Automated AI translations turn the mono-lingual `Article` into a multi-lingual one via an `ArticleTranslation` **sidecar** (1:N from `Article`, cascade; denormalized `clientSiteId`). The source `Article` stays the canonical carrier of the primary language + all language-neutral data (views, comments, reactions, polls-as-entities, series); translations are pure per-language renditions. Migration `20260604120000_article_translations`.

- **Lifecycle as queue.** `status`: `PENDING → TRANSLATING → READY → PUBLISHED` (+ `STALE` on source edit, `FAILED`). Body fields (`slug`/`title`/`content`) are **nullable** — a queued row is a translation _request_ without a body until the cron fills it. `@@unique([articleId, language])` (one row per language) + `@@unique([slug, clientSiteId, language])` (localized slug namespace, separate from the source's `@@unique([slug, clientSiteId])` — locale-scoped routing means they never collide).
- **Config (`ClientSite`).** `translationMode` (`OFF`/`MANUAL`/`AUTO`/`HYBRID`) + `translationLanguages[]` (empty = all supported langs except primary). Set in the AI preferences form (`Form/Client/AI.vue` → `common.preferences.translation.*`). Gated on the active `AI` **ClientFeature** + plan `PRO`/`PREMIUM`/`CUSTOM` (see §6b). The "empty means all" rule lives in one place — `translationQueue.ts → resolveTargetLanguages`, shared by the enqueue cron and the review panel's endpoint, tested in `tests/server/ai/translationQueue.test.ts`; read as "none" it would silently disable translation for every tenant that never picked languages.
- **Engine (deterministic).** `server/utils/ai/translate.ts → generateTranslation` uses `aiModel('translation')` (GPT-6 Luna with explicit medium reasoning, up to 20k tokens for the translated output plus 8k of middleware headroom for reasoning). Poll/embed/img blocks are **masked out with cheerio** before the model sees them (`maskContentBlocks`) — `data-poll-id`/`optionId`/image `src` never travel through the LLM as free text; poll question+labels, image `alt`/`title`, **and human-readable attributes on surviving elements (`title`/`aria-label`, e.g. link tooltips — replaced in-place with `[[ATTR_n]]` tokens)** are translated as ordered structured fields and zipped back onto server-held markup on `rebuildContent` (empty/absent alt stays untouched → decorative images preserved; attribute values are **HTML-escaped** on re-injection so a translated `"`/`&` can't break out of the attribute). Twitter embeds restored verbatim. Pure of billing — the caller logs usage via `recordAiUsage('TRANSLATE_ARTICLE')`.
- **Two trigger paths.** (1) On-demand `POST /api/articles/[id]/translate` (MANUAL/HYBRID); (2) cron `server/tasks/translate-pending.ts` (every 5 min) drains `PENDING`/`STALE` with a **per-row atomic claim** (guarded `updateMany` → `TRANSLATING`) so concurrent runs never double-translate — AUTO → `PUBLISHED`, HYBRID → `READY` (awaiting review), out-of-budget rows release back to `PENDING`. Enqueue/STALE is wired into all four publish paths via `server/utils/ai/translationQueue.ts → syncArticleTranslationQueue` (`articles/index.post`, `[id]/index.patch`, `publish-check`, `generate-article`). STALE keys off an explicit content-change signal, not `Article.updatedAt` (bumped by the view counter), to avoid token churn.
- **Shared slug dedupe.** `server/utils/ai/translationSlug.ts → dedupeTranslationSlug` (used by both endpoint and cron). SEO rendering: see §8.
- **Every endpoint the article page calls must resolve the slug the same way** (`server/utils/articleBySlug.ts → resolveArticleBySlug`, `tests/server/articles/articleBySlug.test.ts`). On a non-primary locale the URL carries the `ArticleTranslation` slug, which does not exist on `Article` at all. `[id]/index.get.ts` handled that; `[id]/related` never did, and its `findUniqueOrThrow` turned it into an unhandled **500 on every `/en` article view** — latent until publishing a translation plus the mismatched-locale redirect made translated slugs actually reachable. The resolver is now shared: translation first (`PUBLISHED`, or any status for an admin), source row as fallback for an untranslated locale, `null` → 404 rather than P2025. `related` also localizes its cards via `localizeArticles` and is **scoped to `clientSiteId`** — `Tag.clientSiteId` is nullable, so a global tag matched articles across tenants.
- **Translation review.** `READY` means "awaiting review". The editor's translation menu and language tabs expose the review state and actions for saved articles; approving publishes the translation. The disconnected admin queue banner was removed along with its unused locale keys.
  - Dirty tracking treats empty editor HTML (`<p></p>`, blank paragraphs) and an empty untranslated body as equivalent, using `hasArticleBody`; real text, media and formatting edits still count. `translateNow` confirms before replacing unsaved text and fences that confirmation to the same language, row version and draft. An untouched missing translation starts immediately and remains visible through background polling.
  - Endpoints: `GET /api/articles/[id]/translations` (rows + `targetLanguages` + mode), `GET /api/translations?status=` (tenant queue), `PATCH /api/translations/[id]` (edit / approve), `DELETE /api/translations/[id]` (discard).
  - **These endpoints pin `clientSiteId` explicitly on top of the ZenStack policy.** `ArticleTranslation`'s read rule is `status == 'PUBLISHED' || (admin && own site)` — the first clause is deliberately unconditional so public article pages can render translations, which means a bare policy-scoped query would have let one tenant's admin list _other_ tenants' published translations. The policy is right for the public path and wrong as the only isolation for an admin listing; both layers apply here.
  - A human edit flips `source` to `HUMAN` — the audit column must stop claiming a machine wrote text a person rewrote. `PUBLISHED` is refused unless title+content exist, so a body-less queue row (`PENDING`/`TRANSLATING`/`FAILED`) can't be published into a blank localized page with a `hreflang` pointing at it.
  - **Language is a dimension of the article, not an appendix.** The reviewer used to be `Article/Translations.vue`, a panel at the very bottom of the editor — below a Tiptap body of unbounded height, so nothing said it existed. That component is gone. `admin/editor/[id].vue` now carries `Article/Editor/LanguageTabs.vue` (a segmented control in the sticky header, stacked below it under `sm`): the source tab plus one tab per target language with a status dot. Selecting a language swaps the **same** title/excerpt/body fields over to that translation, and the header's Save/Publish become Save / _Approve & publish_ acting on it. Language-neutral surfaces — AI composer, cover uploader, MetaBar, drafts — render only on the source tab, because they belong to the article rather than to one rendition of it; the translation tab shows a status strip (source, timestamp, unsaved marker) with _Translate again_ / _Discard_ instead.
  - `app/composables/useArticleTranslations.ts` owns that state: `activeLang === ''` means the source, so the page branches on one flag instead of tracking two ideas of "current language". It is `reactive()`-wrapped at the call site so the template reads `tr.isSource` rather than `tr.isSource.value`. The page routes the shared textareas through `titleModel`/`excerptModel`/`bodyModel` computeds, so `useTextareaAutosize` stays bound to one thing while the underlying target changes. `hasChanges` folds in `tr.isDirty`, or leaving the editor would silently drop a rewritten translation.
  - Pure logic lives in `shared/utils/articleTranslations.ts` (`tests/unit/articleTranslations.test.ts`): `translationHasBody` (the condition Save renders on), `isTranslationDirty` (the condition it is enabled on), `countAwaitingReview`, `resolveActiveLanguage`, and `translationStatusDot`. `resolveActiveLanguage` also fixes a latent bug in the old inline `watchEffect` — it picked the first `READY` row without checking it is still a configured target, so a leftover translation for a language dropped from settings selected a tab that is not rendered.
  - **Listings are locale-aware** (`shared/utils/articleLocale.ts` + `server/utils/articleLocale.ts`, `tests/unit/articleLocale.test.ts`). Until now neither `by-clientsite/[slug].ts` nor `featured/[slug].ts` touched `ArticleTranslation` at all, so an `/en` visitor got Czech titles linking to Czech slugs and a published translation was reachable only via `hreflang` or Google — tokens were being spent on pages nobody could click to. Both endpoints now take `locale` and overlay each card with its `PUBLISHED` translation. `overlayTranslation` only swaps when the row has **both** slug and title, since localized text pointing at the primary-language URL is worse than no translation; the excerpt may fall back. Two things to keep in mind: the feed's Redis key carries `:loc=` (the cached payload is localized, so two locales must not share an entry), and `localizeArticles` filters `status: 'PUBLISHED'` explicitly rather than trusting the ZenStack policy, whose read rule also passes for an admin on their own site — otherwise a logged-in admin would see unreviewed drafts in the public feed.
  - **Navigating between language versions** is one component, `Article/LanguageLinks.vue`, on three surfaces. `target="public"` renders localized `NuxtLink`s to each version's own slug; `target="editor"` points every entry at the **source** article (`articleRef`) with `?lang=` picking the tab, because the editor resolves the article by its source slug and the translated slug would 404 there. Dots (`translationStatusDot`) render only for the editor target — on the public page every entry is published, so a dot would encode nothing.
    - _Article detail_ — gated on `hasTranslations` (`alternates.length >= 2`), the same condition as `hreflang`, so a language is never offered that would only fall back.
    - _Admin `Article/Table.vue`_ — a `languages` column, **not** extra rows: the bloat guard from §6b holds. `articles/search.ts` gained `include: { translations: { select: { language, status, slug } } }`, and drafts are visible here on purpose (it is the owning admin's own list, and "awaiting review" is the point). The cell is one `Article/TranslationMenu.vue` trigger (`CS +3`, a dot only for FAILED/READY/STALE); its dropdown lists every language with its status as text, opens that editor tab, and holds translate/retranslate — the row's action menu no longer does. The actions column includes an explicit eye action linking to the public article on both desktop and mobile; title and thumbnail remain links as larger hit targets. On the article detail, `ArticleStatusCell` is the single status presentation and emits its update directly to `ActionsBar` — a second published badge would duplicate both label and meaning.
    - _Editor_ — `?lang=` is read on load (primary language ⇒ source tab, which the composable stores as `''`), plus an `mdi:open-in-new` link to the live page of whichever language is on screen. It is passed as `useArticleTranslations(id, initialLang)` rather than assigned to `activeLang` afterwards, and the reconciling `watchEffect` is gated on `status === 'success'`. Both matter: an empty `targetLanguages` means _either_ "this site has no targets" _or_ "the request has not resolved", and reconciling against the second silently reset `?lang=en` to the source tab before the payload arrived — the deep link looked like it did nothing.
  - SEO framing that drove the above: **translated pages are not duplicate content** — that is what `hreflang` is for, and the untranslated-locale fallback already canonicalises onto the primary URL. The real Google exposure is _scaled content abuse_ (bulk machine translation published without review), which makes HYBRID the safe mode and AUTO the risky one. The review step is therefore load-bearing, not polish, and anything that makes approving expensive pushes tenants onto AUTO.

## 6a. Plan Matrix (`ClientSite.plan` — enum `ClientPlan`)

Marketing names diverge from the DB enum: marketing **FREE** = enum **BASIC**. Enum is the source of truth (`prisma/schema.zmodel:84`); the pricing copy now lives in the separate `../landing` project.

**A literal `@` in any i18n message breaks the production build.** vue-i18n reads `@` as the start of a linked message (`@:key`), so an e-mail address in a message fails with `Invalid linked format`. It only surfaces under `jit: true`, which the build uses and neither `typecheck` nor `vitest` does — write `&#64;` instead (these messages render through `v-html`, so the entity decodes in both the link text and the `mailto:` href).

**Legal texts** (`i18n/locales/*/legal.json`, rendered by `pages/privacy.vue` / `pages/tos.vue`; the cs/en copies) are a **duplicate of the same file in `../landing`** — edit there and copy across, or the two sites drift. The two copies differ only in line endings (app LF, landing CRLF), so compare with `diff --strip-trailing-cr`. The `[[BRACKETS]]` placeholders are filled (as of 10 Aug 2026); the ARES link is built from the IČO, so both change together. The postal address stays out on purpose — ARES carries it. The processor list names no hosting provider on purpose — app, DB and cache run on own hardware, so there is no hosting processor to disclose under Art. 13(1)(e), and the "transfers outside the EEA" paragraph therefore states no baseline region. The LinkedIn section is written to match the retention limits in the LinkedIn API Terms (profile ≤24 h, social activity ≤48 h) — changing what `server/utils/linkedin/` stores means changing that section too. The Search Console section carries what Google OAuth verification for `webmasters.readonly` requires (scope, data, purpose, Limited Use link, deletion); keep it when trimming. AI vendors are named as the category "AI model providers", so swapping a model needs no policy change. Section numbers are plain text: keep them sequential.

**Who may write which `ClientSite` field.** `shared/utils/clientSiteFields.ts` is the single source: `PRIVILEGED_CLIENT_SITE_FIELDS` (`plan`, `tokenLimit`) are **superadmin-only**; everything in `TENANT_EDITABLE_CLIENT_SITE_FIELDS`, including a tenant's own `gamNetworkCode`, is fair game for a site's own admin. `server/api/clients/[id]/index.patch.ts` builds a Zod pick from the applicable list, so a tenant's privileged extra keys are silently stripped rather than rejected. The partition is pinned by `tests/unit/clientSiteFields.test.ts`; it validates field names against generated ZenStack schema metadata. Reactivating a soft-deleted site (`deletedAt: null`) is superadmin-only too; self-deactivation stays open. Side effects must read the **parsed** value, never raw body — `requestedTokenLimit`, not `scalarBody.tokenLimit`.

**Who may read which `ClientSite` field.** Same file, read side: `PUBLIC_CLIENT_SITE_FIELDS` → `publicClientSiteSelect` (a `fieldMask`, i.e. an ORM `select`) is the **only** projection any session-less route may return, and `CLIENT_SITE_SECRET_FIELDS` names what must never join it (`apiKey`, the three `stripe*` ids, token quota + usage, billing amounts, `communityInsight`, AI prompt config, rate assumptions). Being a whitelist, a newly added zmodel field is private until someone lists it; `tests/unit/clientSiteFields.test.ts` walks generated ZenStack schema metadata to assert both lists only name real scalars, that they are disjoint, and that the generated select is exactly the public list. `tests/server/clients/publicProjection.test.ts` pins the routes themselves.

- `clients/slug/[slug].ts` (public, hit by `useClientSite()` on **every** page → lands in the SSR payload) and `clients/[id]/by-userid.get.ts` (public, powers the author card) select through the whitelist. Both previously returned the _whole_ row from raw `prisma`, i.e. every tenant's `apiKey` and Stripe ids were readable by `curl`-ing any blog. `@omit` would not have helped: these go through raw `prisma`, and `ClientSite` is `@@allow('read', true)` anyway, so **the select is the control**.
- `clients/index.get.ts` is `role: 'superadmin'` via `requireDb`. It was session-optional with `getEnhancedPrisma(user)`, and because the model's read policy is `true` that enhanced client happily dumped every tenant row plus each site's users' usernames **and e-mails** to anonymous callers — a reminder that enhanced Prisma only enforces what the policy says, and `@@allow('read', true)` says "everyone".
- `clients/[id]/index.get.ts` (settings source, keeps `apiKey`/Stripe ids for the owner) now 403s unless `id === user.clientSiteId` or the caller is superadmin. The old check was `['superadmin','admin'].includes(role)` with an attacker-controlled `id` — any tenant admin could read any other tenant's full row.
- `clients/status.get.ts` is where owner-only entitlement data lives now (`plan`, `articlesRemaining`, `articleWallet`, `createdAt`, `firstPaidAt`, `focus`, `audience`, a server-derived `trial` summary, `hasActiveSubscription`, and `theme`/`typographyPreset`/`discloseAiContent` for the editor preview). The site id comes **from the session** (`user.clientSiteId`), never a route param, so it has no IDOR surface. Exposed as `useClientSiteStatus()` and consumed by the trial modal, article balance panel, editor reservation state and first-article checklist.
- **`useClientSiteStatus()` fetches through `useRequestFetch()` and returns the `useAsyncData` handle, not `data.value`.** Both halves were bugs: bare `$fetch` during SSR sends no session cookie, so the endpoint 401'd, a `.catch(() => null)` swallowed it, and the `null` was baked into the payload the client never re-fetched — every consumer silently ran on fallback numbers for the whole session (fabricated quota, dead trial modal, dead AI gate). Returning `data.value` then froze the snapshot at setup time, so nothing re-rendered after a top-up. The same `useRequestFetch()` rule as the Colada queries above — it applies to **any** authenticated `useAsyncData` handler. Consumers must not reintroduce fallback constants (`?? 20000`): when the limit is unknown the quota UI hides rather than inventing a denominator, otherwise 0/20000 reads as 0 % and fires the low-token alarm on a full account.

### 6c. Trial has explicit provenance; plan and payment are separate facts

- `checkout.post.ts` creates every trial tenant on `TRIAL_PLAN` (= `PREMIUM`) and stamps immutable `trialStartedAt` + `trialEndsAt`; the trial exercises the whole product including the crons. `ClientSite.plan` is only the entitlement and `firstPaidAt` only records money movement — neither proves trial provenance. `shared/utils/trial.ts` is the one state machine (`NONE | ACTIVE | EXPIRED | ACKNOWLEDGED`) used by expiry predicates and server status. The browser receives only `{ state, endsAt, daysLeft }`, calculated against server time, and never decides expiry from its own clock. Migration `20260913150000_explicit_trial_lifecycle` backfills both timestamps only from historical `TokenCreditGrant.source = TRIAL`, so manually provisioned PREMIUM/CUSTOM tenants with no Stripe subscription can never receive a false expiry modal or cron downgrade. Ambiguous pre-wallet trials intentionally require manual reconciliation; customer protection wins over an inferred downgrade.
- **`stripeWebhook.ts → marksFirstPayment`**: a `trialing` checkout moves `plan` but must not stamp `firstPaidAt`, or the trial ends the day it starts. Both `checkout.session.completed` and the `subscription.updated` trial-end path call `syncPlanFeatures` on whatever plan they resolve.
- **`trial-expiry` cron (`0 5 * * *`) only touches explicitly marked, unacknowledged, card-less trials whose stored `trialEndsAt` elapsed.** The stored deadline means changing `TRIAL_DAYS` affects new trials only. `expiredTrialWhere` also requires `stripeSubscriptionId: null` because Stripe owns a card-backed trial's lifecycle — promoting on conversion, revoking through `revokesPlan` on a failed first invoice — and a cron downgrade would race that webhook mid-conversion. `tests/server/tasks/trialExpiry.test.ts` pins the SQL filter against the state predicate; drift either strands tenants on the trial plan forever or risks downgrading a provisioned customer.
- **`syncPlanFeatures` at signup is deliberately non-fatal** (try/catch, `TRIAL_FEATURE_PROVISIONING_FAILED`). It throws on an unseeded `Feature` catalog — the hazard already documented in §6b — and signup is the one path that must not depend on it; the plan column alone still unlocks the UI.
- **One trial per inbox, ten sign-ups per IP per day.** The landing creates accounts server-to-server, so `checkout.post.ts` takes the visitor IP from `X-Landing-Client-Ip`, trusted only with a fresh `X-Landing-Sig` over `timestamp.ip` (`landingClientIp`); otherwise the request IP. `inboxOwnsSite` (`server/utils/trialInbox.ts`) compares the canonical inbox (`+tags` dropped, Gmail dots ignored) against existing site owners in SQL that must mirror `canonicalEmail`; a repeat inbox gets a BASIC account without trial articles or a Stripe trial (`TRIAL_REPEAT_INBOX`). It relies on users being soft-deleted — a hard delete or e-mail scrub would reopen the trial. Disposable domains are rejected here too; the landing's copy of the list only saves a code e-mail.
- **AI generation requires both an AI-capable plan and one available article.** `generate/index.post.ts` checks `hasAiPlan` and then reserves through `ArticleCreditWallet`; scheduled generation additionally requires the cron feature. Trial expiry downgrades the plan, while its expiring article grant independently becomes unavailable.
- `end-trial.post.ts` refuses tenants without an actually expired trial and stamps `trialAcknowledgedAt` when the author chooses "continue free". It never writes `firstPaidAt`, so dismissing trial UX cannot fabricate payment history.

### 6b. `ClientFeature` is the only source of truth for AI / Sentiment / Crons

Gating used to be split three ways and the halves disagreed, which is how a PREMIUM tenant ended up staring at a settings panel that showed AI, translations and scheduled generation all switched **off** — with a monthly price next to each — while the app cheerfully generated and translated in the background:

1. `ClientFeature` rows → what the settings panel rendered (`activeFeatures`), written **only** by `features.patch.ts`; nothing created them on a plan grant, so a paying tenant had none.
2. `ClientSite.enableAi/enableCron/enableSentiment` → what the translation endpoint and cron actually checked, written **only** at onboarding and never by the toggle.
3. Bare plan checks → `sentiment-analysis.ts`; and `generate-article.ts` checked **nothing** at all beyond `generationFrequency` + tokens, so a tenant who switched AI off still got articles.

Now: **`ClientFeature` decides, everywhere.** The booleans are dropped (migration `20260806120000_plan_features_single_source`, which also backfills rows for existing PRO/PREMIUM sites). **That backfill is an `INSERT … FROM "ClientSite" JOIN "Feature"`, so it silently inserts nothing when the `Feature` catalog is empty** — and the catalog is written only by `prisma/seed.ts`, a dev seed that also mints test users with a hardcoded password and therefore never runs in production. A prod DB can consequently end up with the gating live and no `ClientFeature` row anywhere, which takes `generate-article`, `translate-pending` and `sentiment-analysis` dark at once while everything else keeps working. Symptom to recognise: crons stop touching tenant rows with no error in the log, because the batch query simply matches nobody.

- `planFeatures.ts → planFeatureSync(plan, active)` is the pure decision (activate what the plan covers, revoke what a downgrade dropped, **skip CUSTOM** — that is the à-la-carte plan where operators pick by hand and `billingLockedUntil` carries real billing weight). `syncPlanFeatures(tx, siteId, plan)` applies it and is called on **every** plan transition: all `stripe/webhook.ts` paths (promote, portal plan change, revocation → BASIC), the superadmin plan edit in `clients/[id]/index.patch.ts`, and the dev switch `_dev/plan.patch.ts` — each inside the same transaction as the `plan` write.
- **`syncPlanFeatures` is "make this site consistent with its plan", not just "write feature rows."** After provisioning/revoking it re-asserts the two invariants that outlive a feature: `syncAutoRelease` (see below) and `recalcFeatureBilling`. Anything that changes a plan therefore gets all three effects for free, which is why the dev endpoint was wired in — a locally switched plan used to leave features and billing behind and stop reproducing production.
- Reads go through `activeFeatureFilter(code)` (a relation `where` for cron batch queries) or `hasActiveFeature(db, siteId, code)`. Both take a narrow structural DB type, matching `translationQueue.ts`/`translationSlug.ts`, so either the base or policy-enhanced ZenStack client is accepted. The read path takes `FeatureReadDb` (`clientFeature.count` only); only the write path needs the wider `FeatureSyncDb` (adds `feature` + `clientSite`).
- Backfilled/plan-granted rows get `billingLockedUntil = now()` (no lock): `billableMonthlyTotal` bills nothing outside CUSTOM, so the 30-day anti-gaming window is meaningless for an included feature. **That is exactly why billability cannot key off the lock window alone** — see `billableFeatureWhere` below.
- **`autoRelease` cannot outlive `ARTICLE_CRONS`** (`syncAutoRelease`). The switch is hidden without scheduled generation (`Form/Client/AI.vue`) and costs a danger confirm to turn on, so leaving it `true` through a revocation meant a later re-subscribe silently resumed auto-publishing generated articles. Enforced on both the plan path (`syncPlanFeatures`) and the manual toggle path (`features.patch.ts`, after the AI cascade).
- **Enqueuing translations is itself gated on the AI feature** (`syncArticleTranslationQueue`). `translate-pending` already refused to drain the queue without it, so a revoked tenant still on `translationMode: AUTO` kept piling up invisible `PENDING` rows on every publish — which a later re-subscribe would flush as one burst of months-old translations. `features` is **optional** in the structural `QueueDb` (a concrete Prisma row type has no such key and would not satisfy it otherwise); the select always asks for it and a missing value fails closed.
- **The `Feature` catalog is load-bearing and was seeded by hand.** With gating derived from it, an empty catalog would silently switch every feature off for everyone, so `syncPlanFeatures` **throws** on a missing code instead of skipping it, and `prisma/seed.ts` upserts the three rows (`update: {}` — it never overwrites real prices).
- **Consequence to know:** `sentiment-analysis.ts` used to run for `plan IN (PRO, PREMIUM)`, but `getAllowedFeatures` only grants `SENTIMENT` on PREMIUM/CUSTOM. Gating on the feature makes the matrix authoritative and **stops sentiment for PRO tenants** — that drift was in the cron, not the matrix.
- Panel side: `Form/Client/AI.vue` quoted a per-feature monthly price on every plan even though `billableMonthlyTotal` returns 0 off CUSTOM. Price now renders only for CUSTOM; everyone else gets an "included in your plan" badge (`common.features.includedInPlan`). The three near-identical 45-line toggle blocks collapsed into `Form/Client/FeatureToggle.vue` (a card in a `lg:grid-cols-3` grid with a `USwitch`; active state is the inverted border and icon tile).

### Feature toggles & dynamic pricing (`AI` / `SENTIMENT` / `ARTICLE_CRONS`)

- **Single source of plan→feature logic:** `server/utils/planFeatures.ts` (pure, unit-tested) — `getAllowedFeatures(plan)` (AI+Crons on PRO+, Sentiment on PREMIUM+), `FEATURE_DEPENDENCIES` (Sentiment & Crons require AI), `getMissingDependencies`, `getDependents`, `isCustomPlan` (the à-la-carte plan — features billed individually), `billableMonthlyTotal`. Consumed by both `clients/[id]/index.get.ts` (`allowedFeatures`) and `clients/[id]/features.patch.ts` so the two never drift.
- **Two billing modes**, both applied by the shared `recalcFeatureBilling(tx, siteId, plan, billingPlan)`: **standard plans (PRO/PREMIUM)** → features are _included_, toggling is a free capability switch, `monthlyPayment` stays **0** (the plan itself is the Stripe charge). **CUSTOM** → à-la-carte: `monthlyPayment = Σ billed feature `priceMonthly``(USD);`PERMANENT`billingPlan is comped to 0.`annualFromMonthly`carries the −20 % annual discount. Called from`features.patch.ts` **and** every plan transition, so the stored price can no longer drift from the plan.
- **What counts as billable** is `billableFeatureWhere` = `isActive: true` **OR** `billingLockedUntil > now`, not the lock window alone. The window alone under-billed twice: a feature switched on past its 30 days stopped counting, and — the sharp one — a tenant moved from PREMIUM onto CUSTOM inherited all three features with `billingLockedUntil` already in the past, carrying them à la carte **for free** until someone happened to toggle something.
- **Server-enforced invariants** (not just client gating, closing an IDOR + a broken-access-control gap): admin may only toggle their **own** `clientSiteId` (superadmin any); enabling a feature requires `getAllowedFeatures[code]` (else 403) and its AI prerequisite active (else 400); **disabling AI cascades** — `getDependents('AI')` are atomically disabled in the same transaction. Client mirrors this with a danger confirm modal (`Form/Client/AI.vue → showAiDisableModal`) before disabling AI while dependents are on.
- **Rate card is USD.** `Feature.priceMonthly` holds USD; the whole display layer is USD-base: `GET /api/currency?target=` → `server/utils/currency.ts → usdCrossRate` (CNB daily table cached 6 h via `defineCachedFunction`, cross-converted via CZK, `amount`-normalized, unit-tested), `useCurrencyRate` returns a computed USD→target rate (`1` for USD) — a ref, because a snapshot taken before the fetch settles froze the USD default into SSR, and `Billing.vue`/`AI.vue` **multiply** USD amounts by the rate (was CZK-base divide). CZK is now just another display currency.

Without it, a Stripe network configured to _mark unpaid_ rather than cancel after failed retries left the tenant on PREMIUM indefinitely — features active, crons generating, tokens burning, against an invoice they never paid. `past_due` is deliberately **not** revoking: that is the dunning grace period where Stripe is still retrying.

- Scripts: `dev`, `build`, `typecheck`, `test`, `test:watch`, `test:coverage`, `lint(:fix)`, `prettier(:fix)`, `fmt`, `zenstack:generate`, `db:migrate:deploy`.
- Line endings are LF everywhere, pinned in both `.gitattributes` (`* text=auto eol=lf`) and `.prettierrc` (`endOfLine`). On Windows a checkout under `core.autocrlf=true` writes CRLF, Prettier rewrites it to LF, and every file's cached size then mismatches — `git status` reports the whole tree modified while `git diff` is empty. Recover with `git add --renormalize .`.

- **Test coverage is partial.** Vitest suites exist under `tests/server/**` (stripe webhook, linkedin publisher + oauthState signing + token refresh, notifications poll, articlePolls, AI translation mask/rebuild + slug dedupe + queue) — server-side pure logic is covered; component/page coverage is still thin.

  - **`scheduledTasks` register per replica.** `nuxt.config.ts::nitro.scheduledTasks` defines the current task names/cadences, gated to production outside browser tests; `shared/utils/operations.ts` defines monitored intervals. Several jobs have DB claims, leases or advisory locks, but this does not certify every task for arbitrary replica counts. Review the scheduler topology and each job's idempotency before scaling or moving execution to a dedicated worker/external scheduler. Retained advertising code remains halted.
  - **No standalone queue worker is shipped.** Current background work runs through Nitro tasks and database-owned work/claim records. AWS SQS or another queue/worker topology remains a separate design decision, with no installed SQS client or queue implementation to infer from historical notes.
  - **Cache provisioning is deployment-specific.** Source supports optional `REDIS_URL`; local Compose does not start Redis/Valkey. Verify availability through the operator status endpoint and deployment configuration rather than treating an old migration note as current runtime evidence.
- Mixed-locale routing (Czech slugs in `pages/`) — intentional, paired with `@nuxtjs/i18n`.
- **Article translations + real `hreflang` (implemented).** Articles are translated per-language via the `ArticleTranslation` sidecar (see §6 → _Article Translations_). `pages/clanky/[slug].vue` resolves content locale-scoped (primary language → source `Article`; other locale → its `PUBLISHED` translation, falling back to the source as a legacy i18n alias when none exists). Once ≥1 translation is published, the page emits real `hreflang` + `x-default` and self-canonicalises per locale; with no translation it canonicalises untranslated locale aliases onto the primary-language path. hreflang is therefore only emitted for translations that actually exist, never speculatively.
- **One canonical origin for the whole app** — `useCanonicalOrigin()` (`app/composables/`, wrapping the pure `buildCanonicalOrigin`/`toAbsoluteUrl` in `shared/utils/seo.ts`, tested by `tests/unit/seo.test.ts`). It derives the origin from the _request_ host, which is mandatory here: every tenant lives on its own domain, so a hardcoded `i18n.baseUrl` / `site.url` would stamp the wrong host on every client site. It forces `https:` outside dev (a proxy that drops `x-forwarded-proto` would otherwise emit `http:` canonicals) and strips a leading `www.`. `pages/clanky/[slug]`, `stitky/[slug]` and `autor/[name]` all build canonical/alternate/JSON-LD URLs from it — the last two previously used a raw `${protocol}//${host}` and disagreed with the article page on `www`.
- **The i18n-generated `hreflang` links are absolutised in `app.vue`.** `useLocaleHead()` prefixes its `link` entries with `i18n.baseUrl`, which is unset (and cannot be set statically — see above), so it emitted **relative** `href`s on `i18n-alt-*` / `i18n-xd`; search engines ignore relative hreflang, which is what a Bing audit of `pixbo.topiqu.com` flagged. `app.vue` now maps `i18nHead.link` through `toAbsoluteUrl(href, canonicalOrigin)` before spreading it into `useHead`, so every generated alternate is fully qualified per tenant. Already-absolute hrefs pass through untouched, so this stays correct if `baseUrl` is ever configured.

## 8a. AEO / GEO Surface

Everything a search or answer engine reads. All of it is per-tenant, resolved from the request host via `server/utils/tenant.ts → tenantByHost` (`cachedTenantByHost` for hooks that fire on every request). Root hosts (`topiqu.com`, `app.topiqu.com`) resolve to `null` and serve none of it.

- **The article body reaches the crawler.** `Article/Parsed.vue` used to split the stored HTML in `onMounted` behind an `import.meta.client` guard, so the served markup contained an empty container — and GPTBot, ClaudeBot, PerplexityBot and CCBot do not run JavaScript. The split now happens in `articles/[id]/index.get.ts` via `server/utils/articleBlocks.ts` (cheerio) and ships as `blocks` on the payload. Shaping rules live once in `shared/utils/articleBlocks.ts`; the editor preview adapts `DOMParser` onto the same builder (`app/utils/articleBlocks.ts`). Adjacent HTML nodes merge into one run — a wrapper per node breaks the adjacent-sibling rules `prose` depends on. Stored body images remain raw HTML, but `Article/Parsed.vue` now injects Nuxt Image/IPX WebP candidates through `shared/utils/articleImages.ts`. Every image retains its direct upload in `data-original-src`; a failed proxy response removes `srcset` and retries that upload, so responsive delivery cannot make the article unreadable.
- Card and homepage lead excerpts go through `articleExcerpt` (`shared/utils/articleBlocks.ts`): the author perex is shown whole (≤500 chars by schema), the body fallback is cut at a word near 240 chars. The homepage feed and featured endpoints apply it server-side and drop `content` from the payload.
- **Heading anchors** come from `headingSlug` (NFKD, so `Přehled trhu` → `prehled-trhu`, not `p-ehled-trhu`). `stampHeadingIds` writes them on save (POST/PATCH); the block builder stamps any body that predates that, and never overwrites an existing id. `Article/TOC.vue` only generates ids for the editor preview.
- **Article slugs** are normalized by `shared/utils/articleSlug.ts` in the editor and in POST/PATCH (409 on a tenant clash). Changing the slug of an article that was ever published stores the old one in `ArticleSlugRedirect`; the article API answers an old slug with 404 + `data.movedTo`, which `clanky/[slug].vue` turns into a 301. A live article always wins the lookup, so a redirect is only re-aimed (upsert) when its slug is freed again. The same function builds cron and translation slugs; translation slugs have no redirects yet.
- **Structured data is one linked graph**, not three hand-built `ld+json` blobs. `app.vue` defines only the Organization identity — `nuxt-schema-org`'s i18n plugin already emits WebSite and WebPage with locale-aware `@id`s off the per-tenant site config, and redefining them detaches `WebPage.isPartOf`; `useArticleSeo` adds Article/BlogPosting, the author Person (`{authorUrl}#author`, the same `@id` `autor/[name]` defines) and any FAQ questions; `useBreadcrumbItems({ overrides })` owns BreadcrumbList — passing overrides rather than remapping its result, because it emits the schema from its own items. `Article.sources` becomes `citation`, `publishedAt` becomes `datePublished` (`createdAt` is when the draft was opened), and `totalWords`/`readingTime` become `wordCount`/`timeRequired`. A second bare `#organization` node next to `#identity` is the module's own logo node, not a duplicate.
- **Sitemap** is entirely `server/api/__sitemap__/urls.get.ts`; `excludeAppSources` and `autoI18n: false` turn off the module's own discovery, which only ever finds the app shell. It emits alternates only for `PUBLISHED` translations, and skips the homepage for a tenant with no articles and tag/author pages on BASIC — in both cases the page itself emits `noindex`, and a sitemap must not contradict it.
- **LLM surfaces:** `/llms.txt` (tenant index, links each article as markdown), `/md/{locale}/{segment}/{slug}[.md]` (`server/utils/articleMarkdown.ts`, cheerio → markdown, no new dependency) and `/rss.xml`. The markdown variant is prefixed rather than a bare `<url>.md`: Nitro cannot bind a param owning part of a segment, and a top-level catch-all would swallow every page route.
- **`shared/utils/routes.ts`** restates the `i18n.pages` segments because Nitro has no `localePath`. `tests/unit/routes.test.ts` asserts them against `nuxt.config.ts` — without it, renaming a route silently points every sitemap, feed and llms.txt URL at a 404.
- **Site identity is per-request.** `server/plugins/siteConfig.ts` pushes the tenant's name/description/locale into the site-config stack above `SiteConfigPriority.runtime`. `nuxt-seo-utils` builds `titleTemplate` and `ogSiteName` from `site.name`, so without it every tenant's pages were titled `… | Topiqu AI Blog` and inherited the platform's Czech description. A tenant with no description pushes `''`, not nothing, so the platform line is suppressed rather than borrowed. `seo.metaDataFiles` is off: it baked `public/favicon.ico` (with `sizes`) into every head and browsers preferred it over the tenant favicon; `app.vue` owns the icon links.
- **hreflang on articles is owned by the page.** `useLocaleHead` derives alternates from the route alone, so it advertised a translation that may not exist; `app.vue` filters its `alternate` links out on the article route. `x-default` is `alternates[0]`, which the API builds as the source language.
- **Extraction fields.** `Article.answer` / `keyTakeaways` / `faq` (mirrored on `ArticleTranslation`) are what an engine quotes. They are opt-in per format/article — a padded FAQ on every post reads as generated and is the pattern engines demote. The editor and its preview render these fields with the same `ArticleSummary` / `ArticleFaq` components as the public article, because they live outside the TipTap HTML body. `readFaq` (`shared/utils/articleFaq.ts`) narrows the Json column; `FAQPage` is emitted only when it is non-empty. **The mirror is only as good as the write** — `generateTranslation` translates and bills all three, but both write sites build their own `data` object, so a dropped field costs the tokens and then renders the source language under a translated body (`tests/server/ai/translationRow.test.ts` pins both). `[id]/index.get.ts` falls back to the source article per field, which is what makes the drop look like a feature gap instead of a bug.
- **Crawl budget:** private paths are disallowed in `robots.txt` (the module re-emits each under every locale prefix, so they are listed bare), answer-engine crawlers get an explicit allow group, and `CRAWL_LIMIT` raises the global 70/10 s rate limiter on the read surfaces — a crawler working through a sitemap otherwise collects 429s and the pages behind them never get indexed. `CRAWL_ROUTES` derives those rules from `LOCALIZED_SEGMENTS` (homepage, article, tag and author paths in every locale) plus `/md/**`; hardcoded, they once covered only `cs`/`en` articles.
- **`Article.contentUpdatedAt` is the modification date**, not `updatedAt`: the `Base` `@updatedAt` also moves on every view counter increment and status flip, which made every visited article claim a fresh edit in `dateModified`, sitemap `lastmod` and the `.md` `Updated:` line. It is set only after first publication, when reader-visible text changes (`changesReaderText` in `server/utils/articleModified.ts`: PATCH, autopilot and its rollback, content actions) and is server-owned (stripped from the PATCH body). `articleModifiedAt` falls back to `publishedAt`. Translation rows keep their own `updatedAt`; a translation leaves the sitemap as `STALE` and returns only when re-translated, so it stays honest.
- **IndexNow** (`server/utils/indexNow.ts`, Bing/Seznam/Yandex): `announceArticle` runs next to the article webhooks (create, PATCH status/text/slug, delete, `publish-check`, cron, autopilot, content actions, translation publish). A live article sends its source and published translation URLs; removals pass the old URLs, computed before they disappear. The key is an HMAC of the tenant id served at `/indexnow.txt`; production only, never on an unverified custom domain, and failures are reported, never thrown.
- **Homepage pagination is crawlable.** "Next" is a real `?page=N` link (`pages/index.vue`); with JavaScript the click appends in place. SSR reads `page`, so every article is reachable by links, not only through the sitemap. `nuxt-seo-utils` keeps `page` in the canonical; a page past the end is `noindex`.
- **Bot lists live in `shared/utils/crawlers.ts`**, imported by both `nuxt.config.ts` and the runtime. Three fetching groups (`ANSWER_ENGINE_BOTS` retrieval/user-triggered, `TRAINING_BOTS` corpus, `SEARCH_BOTS` classic) plus `AI_GROUNDING_TOKENS`, which are **not** crawlers — `Google-Extended` and `Applebot-Extended` have no user agent at all and exist only as robots.txt control tokens for Gemini and Apple Intelligence, so they are absent from `detectCrawler`. Matching is longest-token-first or `Claude-SearchBot` resolves as `ClaudeBot`.
- **`server/plugins/crawlerLog.ts`** ships one Better Stack line per crawler hit on a content route (`source: 'crawler'`, bot, kind, host, path, status, `rateLimited`). Assets are excluded — they are the volume and say nothing about coverage. This is the only way to answer whether the AI crawlers arrive at all, whether they reach `/llms.txt` and the `.md` variants, and whether the rate limiter is turning them away.
- **AI visibility turns those diagnostics into tenant analytics without pretending they are citations.** The crawler plugin also upserts one `AiCrawlerDaily` bucket per tenant/day/bot/path; it stores counts and response outcomes, never IPs or raw user agents. Consented article-view posts classify a small explicit allowlist of AI referrer hosts into deduplicated `AiReferralVisit` rows. `/admin/visibility` keeps these observed signals separate from sampled citation coverage. A tenant with no prompts and no AI traffic gets a single onboarding card instead of empty sections. Each prompt carries `latestRuns` (latest run per provider via `DISTINCT ON`, configured providers only), which `promptOutcome` in `shared/utils/aiVisibility.ts` rolls into one verdict; coverage metrics count every run in the 30-day window. `AiVisibilityPrompt` checks run manually or weekly per prompt for PREMIUM/CUSTOM tenants (the `ai-visibility-monitor` task runs daily, interleaves tenants and caps a run at 300 prompts) against every configured native search API: OpenAI, Claude, Grok, Gemini, Meta Muse Spark and Mistral. Missing provider keys disable only that adapter; provider failures are isolated into separate runs. Only machine-readable citations attached to the provider answer become `AiCitation` rows. Runs retain their answer, model, usage and failure, log aggregated usage to `AiUsage`, serialize per prompt with a PostgreSQL advisory lock and log completion/failure to Better Stack and the audit chain. Two external-citation samples with no owned citation create an `AiVisibilityOpportunity`; the prompt's own `articleId`, else an overlap match, points to an existing article, otherwise the action opens a prefilled new-article AI composer; `HIDDEN` domains are left out of its `citedDomains`. Dismissed opportunities stay dismissed, resolved gaps reopen if they regress, and any owned citation resolves an open gap. The UI has no separate opportunity list: an open one sits on its prompt's row (`Stats/Visibility/PromptRow.vue`: create/improve button, cited-domain chips, dismiss in the row menu), those prompts sort first, and the list shows five before "show all". All coverage copy says “sampled”: provider APIs do not expose every private user conversation. Provider keys are listed in `.env.example`; Anthropic also needs web search enabled for the organization. Answers are markdown and render through `shared/utils/answerMarkdown.ts` + `Stats/AnswerMarkdown.vue` (template-only, no `v-html`; http(s) links only). Pausing a prompt stops the scheduled checks, not a run in flight.
- **Tenants do not write the prompts.** `server/utils/ai/visibilityPrompts.ts` tops each eligible tenant up to `AUTO_PROMPT_LIMIT` (10) active generated prompts, at most weekly (`ClientSite.aiPromptsSeededAt`), with one model call over its top Search Console queries, latest published articles and reader comments containing a question; `focus`/`audience` covers a tenant with none of those. The `ref` the model returns sets `source` (`SEARCH_CONSOLE`/`ARTICLE`/`COMMENT`/`GENERATED`) and, for articles, `articleId`. Every existing prompt, paused ones included, is passed as do-not-repeat, so a paused question is not regenerated; for the same reason the UI offers delete only on `MANUAL` prompts. `retireSilentPrompts` pauses a generated prompt after 21 days of successful runs with no citation of any source — no engine searches the web for it, so it can never produce an opportunity — and the next seeding fills the slot. Seeding runs first in the task, so new prompts (`lastRunAt: null`) are checked the same morning.
- **Competitors are derived, not configured.** `citedDomains` in `shared/utils/aiVisibility.ts` counts each non-owned domain once per answer over the 30-day window. A domain cited for at least `max(2, min(3, ⌈20 % of prompts⌉))` distinct prompts is a competitor; `isReferenceDomain` (encyclopedias, forums, social and AI platforms, `.gov`/`.edu`, `gouv.fr`, `bund.de`) is reported as a general source instead, because an article cannot outrank it. `share` shares its denominator with the tenant's citation coverage so the two are directly comparable. `AiVisibilityDomain` holds the tenant's override (`COMPETITOR` promotes, `HIDDEN` removes), written by `PUT /api/ai-visibility/domains`.
- **`bun run seo:check <origin>`** (`scripts/seo-check.ts`) fetches the whole surface as GPTBot and exits non-zero on failure: body present without JavaScript, sitemap lists articles, llms.txt/rss/markdown reachable, canonical self-referencing, tenant brand in the title, one `h1`, and the schema graph complete with no dangling `@id`. That last check is what caught `WebPage.isPartOf` pointing at a WebSite node that no longer existed.

## 9. Observability — errors, traces and document metrics

### Why we adopted this

Error tracking complements database audit, bounded external logging and monitored Nitro tasks. The client/server Sentry initializers and consented Web Vitals plugin describe what ships. Older SQS, Session Replay and provider-cost notes were proposals or historical rationale; they are not enabled capabilities or measured cost evidence.

### Delivery and limits

- `NUXT_PUBLIC_SENTRY_DSN` selects the Sentry-protocol error/metric destination. Local SDK transport tests do not establish provider-side ingestion, feature compatibility or current prices.
- `server/utils/logger.ts` independently uses `BETTERSTACK_SOURCE_TOKEN` and `BETTERSTACK_INGEST_HOST`; missing configuration disables that external transport. Console output and database audit remain available.
- **Provider error text stays server-side.** AI provider failures (quota, billing, raw response bodies) are kept in audit rows, `ArticleGenerationSession.failureReason`, `AiVisibilityRun.error` and the logs, but tenants only receive localized generic messages: the manual generation stream, `/api/articles/generations/*` and `/api/ai-visibility/*` never return the raw message. `tests/server/ai/manualGenerationStream.test.ts` and `visibilityMonitoring.test.ts` pin this.
- The client initializer has no explicit trace sampling or Replay integration. The server initializer configures trace sampling; the separate browser Web Vitals plugin samples only consenting production documents and sends coarse metrics. Adding Session Replay would require an explicit product/privacy decision and verified configuration.

### Files / wiring

- `sentry.client.config.ts` (project root) — SDK init from `runtimeConfig.public.sentry`. Empty DSN disables the SDK (local / CI).
- `sentry.server.config.ts` reads `process.env` and must also work before a Nitro context exists. Calling `useRuntimeConfig()` there can kill startup. SDK11 bundles this initializer into Nitro through its module; no separate runtime preload or deprecated `autoInjectServerSentry` option is needed. Never initialize it twice.
- `shared/utils/telemetryPrivacy.ts` explicitly disables automatic user/IP, cookies, headers, bodies, query parameters, AI inputs/outputs, database query data, queue/GraphQL payloads and stack-frame variables. Static tracing preserves `beforeSendTransaction` redaction and the legacy transaction envelope. Authentication scrubbing covers the envelope's dynamic sampling context as well as its event body. `tests/server/telemetryPrivacy.test.ts` exercises actual SDK transport with synthetic metadata and no external requests; provider ingestion still needs an authorized runtime smoke.
- `nuxt.config.ts` registers `@sentry/nuxt/module`, public DSN/environment, top-level build upload options (`sentryUrl`, `org`, `project`, `authToken`) and hidden client source maps. Build-plugin telemetry is disabled.
- `server/utils/logger.ts` emits one JSON line per record to the container and the same sanitized record to Better Stack. `LOG_LEVEL` defaults to `info`; ordinary successful reads are `debug`, mutations are `info`, slow requests and client failures are `warn`, and server failures are `error`. Secret/content fields, personal records, email addresses, raw IP/User-Agent fields, URL credentials/query strings and configured credential values are redacted centrally; context depth, strings, arrays and total size are bounded. Login diagnostics use the existing peppered IP fingerprint without retaining the address or browser signature; rate-limit keys and thresholds are unchanged. Error causes retain only bounded name/message/code/status/stack fields, with cycle protection and at most three levels. The external queue remains capped at 200 records with a five-second delivery timeout; delivery/overflow warnings are rate-limited and console records remain available.
- `server/plugins/errorLogging.ts` instruments Nitro `request`, `error` and `afterResponse` hooks. `utils/requestLog.ts` gives each request a server-generated `x-request-id`, hostname, effective protocol, query-free path, status, duration and a stable reason code. Thrown errors and returned failure statuses are recorded once per request; errors without a request are also reported. Expected HTTP 4xx failures omit stacks throughout their cause chain, while 5xx errors retain diagnostic stacks. Domain authentication rejects explain `AUTH_HOST_UNAVAILABLE` or `AUTH_HTTPS_REQUIRED` without exposing domain records. Monitored task completions/failures carry the existing task run ID and outcome, while database audit remains unchanged.
- **Both channels only see errors nobody caught.** Sentry auto-captures what escapes a handler; `errorLogging.ts` sees what Nitro turns into a 5xx. A `try`/`catch` that returns a fallback satisfies neither, so every deliberate swallow is invisible in production unless it reports itself — `server/utils/reportError.ts → reportCaughtError` (`Sentry.captureException` + `logger.error`) is that call. The explicit name avoids colliding with h3's one-argument `reportError` auto-import. It matters most where a failure is _designed_ to be non-fatal: best-effort image generation, stock-provider fallbacks, and `articles/generate` — a streamed handler has already sent its 200, so it structurally **cannot** produce a 5xx and no amount of Nitro-level hooking will ever cover it.
- `.env.example` — `NUXT_PUBLIC_SENTRY_DSN`, `SENTRY_URL/ORG/PROJECT/AUTH_TOKEN`.
- Session Replay is not configured, so no masking or replay-worker behavior is claimed. Existing CSP allowances do not activate a telemetry feature.

### Notification delivery

- `Notification/Bar.vue` renders the list and owns optimistic deletion; `useNotificationPolling` owns single-request polling, cancellation, visibility, retry delays and connection state. A 401 rechecks the session once, a 403 pauses until explicit retry or a changed user, and transient failures back off to five minutes (429 honors `Retry-After`). Transient session-check failures preserve an established session. User switches and disposal abort pending polls and ignore their late responses; the popover explains a paused connection without repeated error toasts.
- The list seeds a server-side `{ createdAt, id }` cursor even when empty. Polling with `since` plus `sinceId` drains up to 25 rows oldest-first, returns the last delivered cursor and quickly requests remaining batches; equal timestamps are ordered by ID. Cursor progression is independent of displayed/deleted items. Older clients sending only `since` retain newest-first responses. Notification reads remain policy-enhanced and scoped to the authenticated user; no schema migration is needed.

- Article interaction surfaces keep state visible at the control that owns it: comment like/dislike buttons carry their own pressed treatment, the terminal comment-page sentinel says there are no _more_ comments instead of claiming there are none, and `Article/Drafts.vue` uses bounded two-column selectable cards rather than an overlay button that could escape or intercept the card layout.
- `useClientSite()` hands back a plain nullable snapshot because ~16 call sites branch on its truthiness (`if (clientSite)`, `Boolean(clientSite && …)`); a ref or reactive proxy would be truthy everywhere and break them silently. `useLiveClientSite()` returns the ref for the same `useAsyncData` entry, and both go through one `fetchClientSite` so they cannot drift. `Header.vue` needs the live form: it sits in the persistent layout and is never re-created by navigation, so a saved logo would otherwise wait for a full reload. Saving `/settings` calls `refreshClientSite()`; its `getCachedData` returns `undefined` for `cause === 'refresh:manual'`, without which the payload would be served straight back and the refresh would be a no-op. Theme, typography, tagline and description reach the layout through the snapshot and still need a reload.
- The brand-asset editor (`Form/Client/LogoUploader.vue`) is assembled from system primitives: `UFileUpload` for the empty state (it owns the dashed dropzone, drag-and-drop and the dragging state), `USlider` for zoom, `UAlert` for the failure. It previously hand-built the dropzone from a bare `<UButton>`, which defaults to solid primary — the whole 224 px zone rendered as a blue slab and its dashed border and hover states were invisible against it. `useAvatarCropper` exposes `acceptFile` so a file can arrive from a drop, not only from its own file dialog. Transparency behind a logo or favicon is drawn by `.transparency-grid` in `main.css` from `--ui-bg-accented`, so it follows the theme instead of a hardcoded gray per color scheme.
- Templates may only render tags that resolve. `Form/Client/LogoUploader.vue` was written against a `<Modal>` and `Form/Client/IntegrationsCatalog.vue` against a `<FormField>`, neither of which exists — Vue renders an unresolved tag as an empty element, so the brand-asset editor and the analytics fields were mounted but invisible with no error beyond a console warning. Both now use the real components (`UModal` with `#body`, `AppFormField`), and `nuxtUiContract.test.ts` resolves every PascalCase template tag against `app/components/`, Nuxt UI and an explicit external allowlist.
- `AppFormField` with `type="textarea"` and `maxLength` shows a `n/max` counter in the field hint, amber from 90 %. The bio limit is `BIO_MAX_LENGTH` in `shared/utils/profile.ts`, mirroring `@length(0, 300)` in `user.zmodel`; `users/[id]` PATCH enforces it in zod as well.
- A rejected upload always names its reason. `File/Uploader.vue` toasts a `common.upload.*` message with the measured value against the limit instead of a generic failure, and `server/api/upload.ts` returns the same keys translated, so a client-side refusal and a server-side one read alike. The favicon limits are one source of truth in `shared/utils/favicon.ts`. A file the browser cannot decode resolves the probe to `null` — the earlier `Image.onload`-only promise stayed pending forever, which is what made a bad favicon fail with no message at all.
- Custom emoji management is optimistic in both directions: create inserts the local object-URL preview while the upload runs and swaps in the server record on success; delete removes immediately and restores the record at its previous position if the request fails. Related and author article queries project only the current viewer's reaction and collapse it to `likedByUser`, so every `ArticleCard` renders its initial heart state without exposing reactor identities. Author names are URI-encoded before their SSR data request, including generated AI names containing spaces.
- `Article/Collection.vue` keeps pagination outside its card grid so it always spans the collection below the final row. Tenant settings read back the complete editable brand kit (`tagline`, favicon and typography included); omitting a field from `clients/[id]` makes a successful PATCH appear to revert as soon as the form refreshes.
- The tagline is a standfirst, not a kicker: 80 characters is too long to sit beside the logo. The homepage masthead renders it below the name with wrapping, above the lighter description; the empty state uses the same hierarchy. `brandTitle()` puts it in `og:title` only — `<title>` stays the bare name because it is per-page and templated.
- Visual style (`Form/Client/Branding.vue`) follows the onboarding look: inline preset/custom swatches with a labelled hex row in `BrandColorEditor`, selectable font samples in `BrandTypographyEditor`, and a publication preview with the tenant domain as the tagline fallback. `BrandColorInput` supports combined, swatch-only and hex-only presentation; logo palettes, gradient editing and `BrandFontSlot` uploads retain the same state and mutations. Choices are `URadioGroup variant="card" indicator="hidden"`. Grids use container queries (`@md:`): at `xl` the form column is ~390 px beside the preview, so viewport breakpoints split it too early. Below `hasAdvancedBranding` gradient presets are disabled and font slots are not rendered; each shows one `unlockPro` link to `settings?tab=billing`. Gradient presets derive from the accent, so a stored gradient can match none — the "Customize" trigger always swatches the stored one.
- `tests/unit/i18nCompleteness.test.ts` keeps all four locale key sets synchronized, verifies placeholders and HTML tags against English for German and French (including master and email copy), and rejects unresolved static translation calls.
- `tests/unit/languageRegistry.test.ts` checks every place that enumerates languages (schema enum, i18n locales and their `files`, localized pages, shared language tables, number formats, message/master/email files, language names) against `LANGUAGE_OPTIONS`, so a new language fails with the list of what is missing. `tests/unit/i18nMessageSyntax.test.ts` compiles every message, catching stray `@`, unbalanced braces and broken placeholders before runtime.
- `playwright.config.ts` and `tests/e2e/` provide deterministic responsive visual and accessibility checks. They require a separate `TEST_DATABASE_URL` and refuse to reuse `DATABASE_URL`. The `release-smoke` project is deliberately separate from the dev-server matrix: CI first installs with the Docker-pinned Bun version and `--frozen-lockfile`, builds the real Nitro `.output`, then opens a seeded public article with service workers enabled. It verifies same-release JS/CSS availability, rejects SRI on mutable Nuxt chunks, reloads under the active worker, and pins `/sw.js` to a non-cached, non-app-shell navigation configuration.

- Plan and feature mutations use a single database lock order: `ClientSite` first, then `ClientFeature`. `syncPlanFeatures` acquires the parent lock through a normal ORM update (and therefore needs no raw row-lock query); short plan/feature transactions run at serializable isolation and retry PostgreSQL serialization/deadlock errors (`40001`/`40P01`) twice. Membership acceptance/removal likewise orders `User` before `Session`. Scheduled publishing writes its globally serialized audit-chain entries only after the article transaction commits, so the advisory log lock cannot prolong article row locks.

- Article generation quality: manual streaming performs one full fact/copy review and, when needed, one targeted revision before media finalization. It does not repeat the expensive live-web review after that revision: resolved findings remain in the audit metadata, while a failed revision leaves the reviewed original in the editor with a warning. The stricter review-after-revision gate remains limited to unattended scheduled publishing. Selected polls, tables and body images are deliverables rather than optional hints; AI image fallback defaults on for AI-enabled tenants but remains individually disableable and visibly labelled. YouTube remains conditional on a verified URL. The editor hides unavailable format modules, keeps billing explanation compact, and replaces the shared shallow wallet state on reservation/settlement; Stop polls briefly past the HTTP cancellation race until the reservation is released. Review/revision tokens join accounting. YouTube lookup considers both model text and provider-returned search URLs before oEmbed verification. Research briefs retain only lines backed by provider-returned source URLs (`server/utils/ai/researchEvidence.ts`). Image providers require query terms in catalogue metadata before aspect-ratio selection, never shorten subject queries, and `server/utils/images/selection.ts` deduplicates asset/source URLs across cover and body. Documentary misses remain empty only when synthesis is disabled or fails; body images never become duplicate covers. Unseen stock images do not inherit model-invented captions. Repeated content slot markers render once.

- Draft fact verification now performs a fresh forced web search over the written body and modules before copy editing, including on the deep-research path. Retrieved contradictions and UNSUPPORTED MATERIAL verdicts cannot be overridden by copy-desk approval; minor NOT VERIFIED qualifications are advisory. Research and verification accept a rule in force (law, regulation, official requirement) only from text the source shows to be in force; drafts, pending amendments and redlines count as evidence of the proposal only. Source-agnostic by design — no legal-source allowlist. Corrections and verified URLs reach revision and final source filtering; verification usage joins editorial accounting. Manual image synthesis is opt-in via `allowGeneratedImages` (default false); scheduled synthesis respects the AI-capable plan and explicit AI feature disablement. Cover and body both search existing archives even for `generate` intent before considering permitted illustrative synthesis. When permitted, missing documentary images may become explicitly labelled AI illustrations without documentary captions.

- Official first-party media is publisher-agnostic: when images are selected, live research must open and identify the developer/publisher's official product, newsroom, press or download pages. `server/utils/images/press.ts` extracts declared Open Graph, Twitter, JSON-LD, preload, gallery and download assets (including separately hosted CDNs), while ordinary embedded images remain restricted to the official site's host family. Every page and asset fetch (`images/publicFetch.ts`, shared with fact-check and knowledge URLs) is HTTPS-only, re-validates each redirect, DNS-checks against private/reserved networks, **connects to exactly the checked addresses** (a pinned `lookup` on `https.request`; plain `fetch` would resolve again and was open to DNS rebinding) and is byte-capped; accepted raster MIME types are decoded, dimension/aspect validated, converted to WebP and cached on the platform CDN. Credits retain the official page, original asset and any explicit license metadata. A verified official YouTube video's thumbnail is the last first-party candidate before Steam/archive search and the visibly labelled AI fallback. There is no publisher hostname allowlist.

- Game image discovery now queries the official Steam store screenshot catalogue before Openverse/Wikimedia or synthesis, independently of the text citation list (`server/utils/images/steam.ts`). Exact game-name/number matching prevents substituting prior installments, and per-article catalogue caches supply distinct assets for cover and body. Credits always identify the original game and publisher; catalogue shots are labelled illustrations rather than inheriting unverified scene descriptions.

- Body image captions (`ai/articleMedia.ts` → `images/caption.ts`): the writer's caption describes the image it asked for, so only a freshly generated (`kind: 'ai'`) picture uses it, as `alt` only; its figcaption holds just the AI label span, which `Article/Parsed.vue` strips (and then drops the empty caption) for a tenant with `discloseAiContent` off. Searched photos keep provider metadata and the credit line. A credit renders as `Foto: <name> (<licence>)` (`shared/utils/imageCredit.ts → creditSegments`, shared by body captions, the cover and the Shopify export): the name links to the work's page; the licence stays visible because CC 2.0/3.0 require its URI. An illustrative image says so in its credit label (`illustrationBy`), so only an uncredited one gets the bare prefix. A generated cover is marked by a badge on the picture (`Article/Header/Hero.vue`, honours `discloseAi`), not a caption line. The article-level disclosure sits in `ActionsBar`'s meta row: `ArticleView` hands it to the `actions` slot and renders it alone when no slot is given (editor preview).

## Shopify article publishing

Shopify is a Pro/Premium/Custom integration in `Form/Client/IntegrationsCatalog.vue`, configured by `Form/Client/Shopify.vue`; `Article/Editor/Shopify.vue` is the editor header status button and popover for manual sends of the saved source-language article; `Article/Editor/PublishDialog.vue` lets the main Publish button target Topiqu and/or Shopify, and a save that remounts the page (new article, changed slug) hands the Shopify send over in `history.state`. `useShopify` shares tenant-keyed status. `prisma/models/shopify.zmodel` adds `ShopifyConnection`, `ShopifyPublication` and the system-only `ShopifyInstallation` (a store installed but not linked to a project). Tokens use AES-256-GCM and expiring offline refresh with a database lease. The publication worker stores an immutable HTML export, claims each send atomically, and retries temporary failures through `server/tasks/shopify-publish.ts` every five minutes. Unconfirmed creates are reconciled by deterministic handle plus `topiqu.article_id`, never blindly retried. Every send checks tenant publishing permission and the media-rights review. Secrets and export payloads are omitted from responses. Product import creates one `SHOPIFY` knowledge source per connection. Webhooks only queue a current-state sync and are never applied directly, so a late payload cannot restore old facts; a revision counter re-queues `shopify-catalog` when events arrive mid-sync, and a failed read never applies a partial snapshot. Price and stock stay structured facts (no re-embedding). Over the product quota, a stable prefix by Shopify product ID is imported.

The app is embedded with Shopify-managed installation; there is no OAuth redirect and no manual store domain (App Store 2.3). App Home is `server/routes/shopify/index.get.ts`, a Nitro-rendered document outside the Nuxt shell: App Bridge first, Polaris web components, a nonce-bound inline script and a per-shop `frame-ancestors` CSP (nuxt-security applies CSP only to Nuxt-rendered pages). It calls `/api/shopify/app/session`, authenticated only by the App Bridge ID token (`verifyShopifyIdToken`), which exchanges it for offline tokens. A linked store re-exchanges whenever its grant is not `CONNECTED` or lacks scopes, so opening the app is the reconnect. An unlinked or `REVOKED` store gets a `ShopifyInstallation` and a stateless signed link (`signShopifyLink`, 15 min). `GET /api/shopify/link` moves it into an httpOnly cookie plus the readable `shopify_install` marker and lands on integration settings, via `start` after sign-in. `POST /api/shopify/link` needs `INTEGRATION_CONTROL` on the session's project. It moves the installation into a connection and replaces only `REVOKED` rows: a store never leaves a project that still has it connected.

Billing (App Store 1.2.1): `ClientSite.billingProvider`. Linking a project without a Stripe subscription (and not CUSTOM) switches it to `SHOPIFY`, which also needs `BILLING_CHANGE`. Existing Stripe customers stay on Stripe. Shopify App Pricing sends no webhooks: `syncShopifyPlan` (`server/utils/shopify/billing.ts`) reads the Partner API `activeSubscription` on App Home load (throttled to 5 min, forced by the `plan_handle` welcome link), after linking and hourly in `shopify-billing`. Plan handles must start with `pro` or `premium`. A Partner API failure never downgrades. Without a subscription, the plan drops to BASIC only if Shopify had set it (`planHandle`), so a running Topiqu trial stays with the trial job. Allowances go through `grantPlanArticleCredits` (shared with Stripe). Annual plans continue in `grant-annual-article-credits`. Uninstall hands billing back to Stripe; a Topiqu-side disconnect keeps Shopify billing. `rejectShopifyBilled` blocks Stripe subscribe/checkout for `SHOPIFY` projects and while `shopify_install` is set. The Stripe UI (Billing, article packs, upgrade banner, paid plans in `TenantCreate`) is hidden accordingly.

`shopify.app.toml` (embedded, scopes declared here, uninstall/compliance/catalog webhooks) is released with `shopify app deploy`, which replaces the whole remote config. `SHOPIFY_ENCRYPTION_KEY` must never rotate: stored tokens become unreadable.
